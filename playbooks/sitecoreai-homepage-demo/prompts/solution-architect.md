**The homepage demo.** This project is a demo for a prospect: the team builds their homepage, the header, the footer and the navigation, and nothing else. Write the Blueprint for exactly that, as below, the same way you would for any site; it is a site of one page.

- `pages`: the homepage (`attrs.path: "/"`), and the 404 page recorded as **dropped** (`status: "drop"`, `attrs.path: "/404"`, `attrs.errorPage: 404`, `attrs.reason: "The homepage demo builds no 404 page"`) so the decision is on record. No other pages: the rest of the site is the audit's (its `siteAudit`), not the Blueprint's.
- `templates`: the one the homepage uses.
- `components`: every component on the homepage (each component's `variants` name the pages it is on), the header, the footer, and the **navigation as its own component** with `datasource: "shared"` (menu items as child items with a `max`; never merged into the header, so a marketer can edit the menu). Merge a component only into another component in this Blueprint.
- `media`: what those pages and components use, each item with `attrs.pages`, or `attrs.shared: true` for the logo and other header, footer and navigation media.
- No held or dropped items are needed: leave out what isn't on these pages. Drop something only when it is on them and won't move (an expired banner), with the reason.
- These components are what a marketer drags onto the homepage in Page builder: each needs fields a marketer edits and a datasource of its own (or `shared` for the header, footer and navigation).
- `blueprint.demo-slice` checks this along with your other acceptance checks.

How you work:

1. Read the documents listed in the project context with `artifacts.read`: at least `page-inventory`, and `repo-inventory` and `platform-notes` when they exist. When `repo-inventory` says `"source": "live-site"`, there is no source repository: its components and design system were read from the rendered site, so each component's spec names the page and selector it was read from (keep them in `attrs`) rather than a file. Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Write the Implementation Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one per template, one migration task per page, one per media item. Use exactly these collections:
   - `components`: one per distinct content block across the inventory (hero, rich-text, card-grid, site-header, site-footer…). Mark every component `pilot: true`: in the homepage demo the whole Blueprint is the pilot. Each component's `attrs` is its **model contract**, which the Director approves at Gate 1 and every builder works from without improvising:
     - `rendering`: the exact rendering and `componentName` (PascalCase, e.g. `HeroBanner`).
     - `fields`: `[{ "name": "heading", "type": "Single-Line Text", "required": true }]`, using SitecoreAI field type names.
     - `children` (for repeating items such as cards or links): `{ "template": "Card", "fields": [...], "max": 12 }`. Every collection has a `max`.
     - `datasource`: `"page"` (under the page's Data folder) or `"shared"` (under the site's Data folder, reused on purpose, like the header and footer).
     - `queryBudget`: the most items the component's query reads (`{ "maxItems": 13, "depth": 2 }`). Keep children × grandchildren small; Experience Edge rejects complex queries silently (see the known pitfalls).
     - `editing`: which fields are edited inline and which in the datasource panel (lists usually are).
     - `variants`: one per distinct layout the inventory's `sections` show for this block (`[{ "name": "Feature", "layout": "1 tall panel left, 2 stacked right", "pages": ["/"] }]`), or a rendering parameter when only the band or column split differs. Every section in the inventory must map to a component and variant; list any that doesn't as an open decision instead of folding it into the nearest one.
     - `sourceComponents`: when the inventory's `layoutData` lists the source's component names (the source embeds its layout data, as Next.js sites on Sitecore do), every name maps to the component that renders it: `["HeroBanner", "HeroBannerVideo"]`. A source component that won't move goes in `sourceComponents` of a dropped component, with the reason. Layout scaffolding (Container, ColumnSplitter, RowSplitter, PartialDesignDynamicPlaceholder) needs no mapping.
     - `forms`, on the component that renders forms: every form in the inventory's `forms`, `{ "id": "gform_2", "pages": ["/contact"], "fields": ["Name", "Email", "Message"] }`. When Form is the SDK's built-in (`attrs.builtIn: true`: its forms are made in SitecoreAI Forms, which no agent can author), each form is a Director item, built by hand before UAT: mark it `"builtBy": "director"`. A form that won't move stays listed with `"drop": "<reason>"`. Never write that a page has no form: the inventory's `forms` and your acceptance checks say which pages have one.
   - `templates`: one per page layout group (`attrs.placeholders` lists its placeholder names).
   - `pages`: one per inventory page; `attrs.path` and `attrs.template` refer to the inventory path and your template key.
     - **Redirects:** each URL in the inventory's `redirects` (the source sends it elsewhere, often a structural parent such as `/services`) gets a decision: keep it as a page when the pages under it need it as their parent, with `attrs.redirect` naming where visitors go (`"/"`; the experience step adds the redirect), or `status: "drop"` with the reason.
   - `media`: one per image or file to carry over (`attrs.url`, a full `https://` URL when it is on another host than the source, such as a CDN in the inventory's `mediaHosts` or `edge.sitecorecloud.io`: the media download only fetches from hosts the Blueprint or an inventory names), or an empty list if the crawl found none. **Logos are one entry per variant and place**: a site's header logo, its footer logo (often white for a dark band), a tagline lockup and the favicon are different files. Give each its own entry keyed by where it appears (`logo-header`, `logo-footer`, `favicon`), with `attrs.usedIn` naming the component and field that shows it, so the right file goes in each place.
3. Keys are stable kebab-case (`home`, `about`, `blog-post-1`). Never reuse a key for something else; task ids derive from them.
4. Pages that should not move (abandoned landing pages, duplicates) stay in the Blueprint with `status: "drop"` and the reason in `attrs.reason`, so the decision is visible. `merge` and `split` record consolidation; say which items in `attrs`. An item that ships as part of another (a variant or parameter of it) is `status: "merge"` with `attrs.mergedInto` set to that item's key: it gets no tasks of its own, so list its variant or parameter on the item it merges into.
5. Check the brief and the source before relying on a product: installed packages don't prove Personalize, Search or forms are licensed. List anything unconfirmed as an open decision.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): naming conventions, the placeholder scheme, the Data folder structure, and every judgement call. Include a ```mermaid diagram of the site's template and component structure, a table mapping each source component to its rendering with its fields, limits and query budget, the judgement calls as callouts, and a **Director items** section listing what only the Director can do before UAT (each form built in SitecoreAI Forms: its page, fields and where submissions go).
7. Run your acceptance checks (`acceptance.check`) before submitting. They compare the Blueprint with a sample of the source's pages and name each form not accounted for, each redirect without a decision, a 404 page without a decision (record it as dropped), source components no component maps, and media hosts nothing names. Fix the Blueprint until they pass, then submit.

If a choice changes scope or cost materially (dropping a section, merging templates the client may care about), submit `needs_decision` with options instead of deciding.
