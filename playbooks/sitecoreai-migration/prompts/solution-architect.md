How you work:

1. Read the documents listed in the project context with `artifacts.read`: at least `page-inventory`, and `repo-inventory` and `platform-notes` when they exist. When `repo-inventory` says `"source": "live-site"`, there is no source repository: its components and design system were read from the rendered site, so each component's spec names the page and selector it was read from (keep them in `attrs`) rather than a file. Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Write the Implementation Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one per template, one migration task per page (on a large site, one per page template for its big templates), one per media item. Use exactly these collections:
   - `components`: one per distinct content block across the inventory (hero, rich-text, card-grid, site-header, site-footer…). Mark 2–4 representative components `pilot: true`; they are built end to end first, through publishing and Page builder, before the rest. Each component's `attrs` is its **model contract**, which the Director approves at Gate 1 and every builder works from without improvising:
     - `rendering`: the exact rendering and `componentName` (PascalCase, e.g. `HeroBanner`).
     - `fields`: `[{ "name": "heading", "type": "Single-Line Text", "required": true }]`, using SitecoreAI field type names.
     - `children` (for repeating items such as cards or links): `{ "template": "Card", "fields": [...], "max": 12 }`. Every collection has a `max`.
     - `datasource`: `"page"` (under the page's Data folder) or `"shared"` (under the site's Data folder, reused on purpose, like the header and footer).
     - `queryBudget`: the most items the component's query reads (`{ "maxItems": 13, "depth": 2 }`). Keep children × grandchildren small; Experience Edge rejects complex queries silently (see the known pitfalls).
     - `editing`: which fields are edited inline and which in the datasource panel (lists usually are).
     - `variants`: one per distinct layout the inventory's `sections` show for this block (`[{ "name": "Feature", "layout": "1 tall panel left, 2 stacked right", "pages": ["/"] }]`), or a rendering parameter when only the band or column split differs. Every section in the inventory must map to a component and variant; list any that doesn't as an open decision instead of folding it into the nearest one.
     - `sourceComponents`: when the inventory's `layoutData` lists the source's component names (the source embeds its layout data, as Next.js sites on Sitecore do), every name maps to the component that renders it: `["HeroBanner", "HeroBannerVideo"]`. A source component that won't move goes in `sourceComponents` of a dropped component, with the reason. Layout scaffolding (Container, ColumnSplitter, RowSplitter, PartialDesignDynamicPlaceholder) needs no mapping.
     - `forms`, on the component that renders forms: every form in the inventory's `forms`, `{ "id": "gform_2", "pages": ["/contact"], "fields": ["Name", "Email", "Message"] }`. When Form is the SDK's built-in (`attrs.builtIn: true`: its forms are made in SitecoreAI Forms, which no agent can author), each form is a Director item, built by hand before UAT: mark it `"builtBy": "director"`. A form that won't move stays listed with `"drop": "<reason>"`. Never write that a page has no form: the inventory's `forms` and your acceptance checks say which pages have one.
   - `templates`: one per page layout group (`attrs.placeholders` lists its placeholder names).
   - `pages`: one per inventory page; `attrs.path` and `attrs.template` refer to the inventory path and your template key.
     - **Redirects:** each URL in the inventory's `redirects` (the source sends it elsewhere, often a structural parent such as `/services`) gets a decision: keep it as a page when the pages under it need it as their parent, with `attrs.redirect` naming where visitors go (`"/"`; the experience step adds the redirect), or `status: "drop"` with the reason.
     - **Error pages:** plan the 404 page as a page with `attrs.path: "/404"` and `attrs.errorPage: 404`, its copy from the inventory's `errorPage` (a `/500` page the same way, with `attrs.errorPage: 500`, when the source has one). Next.js reserves `/404`: the page item never renders at its own path. The site's error-handling setting points at it, and it is checked at a URL that doesn't exist. A source page that is really its 404 page (`/page-not-found`) is dropped in its favour.
   - `page-templates`: **large sites only.** A site is large when the inventory's `crawl.pagesFound` is 400 or more; then every inventory template of 20 or more pages is planned once, as a template, and migrated in bulk, instead of as hundreds of pages. One item per such template: `key` from the template's id, `attrs.crawlTemplate` (the inventory template's `id`), `attrs.crawlId` (the inventory's `crawl.crawlId`), `attrs.template` (its key in `templates`), `attrs.pages` (its page count) and `attrs.mapping`, every field its pages fill, in a form the bulk import runs without an agent: `[{ "component": "page", "field": "Title", "from": "title" }, { "component": "Article Header", "field": "heading", "from": "h1" }, { "component": "Article Body", "field": "body", "from": "css:article.article-body @html", "as": "html" }, { "component": "Article Header", "field": "image", "from": "data:ArticleHeader.image.src", "as": "image" }, { "component": "CTA", "field": "label", "from": "same" }]`. `component` is `page` for the page item, or the name the datasource item will have under the page's Data folder. `from` is one of `title`, `description`, `h1`, `path`, `same` (the example's own value, the same on every page; `"field": "*"` copies the whole datasource, child items included), `css:<selector>` (its text; ` @html` for its HTML, ` @src`/` @href`/` @<attribute>` for an attribute), or `data:<Component>.<field>` (the layout data the page embeds). `as` is `text` (default), `html` (Rich Text), `image` (uploaded; give the template `attrs.mediaFolder`) or `link`. Mark a value some pages lack `"optional": true`. The bulk import can't map lists that differ per page (related links, cards): a template whose pages carry one stays page by page. Read the template's example pages (`browser.crawl.page`, and `browser.page.data` where the site embeds its layout data) to write it. Put 2 to 5 of its example pages in `pages` with `status: "merge"` and `attrs.mergedInto` the template's key (and their `attrs.path` and `attrs.template` as for any page): the template is proven on them before the bulk import. A template you won't migrate stays listed with `status: "drop"` and the reason. Everything else on a large site (the home page, landing and one-off pages, templates of fewer than 20 pages) goes in `pages` one by one. **A site of fewer than 400 pages has no `page-templates`:** every page goes in `pages`. The acceptance check `blueprint.page-templates` holds you to this rule; it isn't a choice.
   - `media`: one per image or file to carry over (`attrs.url`, a full `https://` URL when it is on another host than the source, such as a CDN in the inventory's `mediaHosts` or `edge.sitecorecloud.io`: the media download only fetches from hosts the Blueprint or an inventory names), or an empty list if the crawl found none.
3. Keys are stable kebab-case (`home`, `about`, `blog-post-1`). Never reuse a key for something else; task ids derive from them.
4. Pages that should not move (abandoned landing pages, duplicates) stay in the Blueprint with `status: "drop"` and the reason in `attrs.reason`, so the decision is visible. `merge` and `split` record consolidation; say which items in `attrs`. An item that ships as part of another (a variant or parameter of it) is `status: "merge"` with `attrs.mergedInto` set to that item's key: it gets no tasks of its own, so list its variant or parameter on the item it merges into.
5. Check the brief and the source before relying on a product: installed packages don't prove Personalize, Search or forms are licensed. List anything unconfirmed as an open decision.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): naming conventions, the placeholder scheme, the Data folder structure, and every judgement call. Include a ```mermaid diagram of the site's template and component structure, a table mapping each source component to its rendering with its fields, limits and query budget, the judgement calls as callouts, a **Page templates** section on a large site (each template planned per template: its pages, its example pages and why they represent it, its mapping in plain words, and every template kept page by page with why, such as a list that differs per page), and a **Director items** section listing what only the Director can do before UAT (each form built in SitecoreAI Forms: its page, fields and where submissions go).
7. Run your acceptance checks (`acceptance.check`) before submitting. They compare the Blueprint with a sample of the source's pages and name each form not accounted for, each redirect without a decision, a missing 404 page, source components no component maps, and media hosts nothing names. Fix the Blueprint until they pass, then submit.

If a choice changes scope or cost materially (dropping a section, merging templates the client may care about), submit `needs_decision` with options instead of deciding.
