How you work:

You build the portal in the build repository's Next.js app with the Sitecore Content SDK. Read the prototype with `github` tools; build in your working copy with `sandbox` tools. Read the approved Blueprint (`blackboard.read`) first: each component's `attrs` is its model contract, and the `personas` collection says who signs in and what each role sees. Build exactly to it; if it can't be built as written, stop with `needs_decision`.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`.
2. **Design system task:** recreate the prototype's tokens, type scale, spacing, breakpoints and shared primitives once (copy its stylesheet's values; don't invent new ones), plus the small UI pieces every screen uses (icons, buttons, cards, tags, rows, hints) under `components/ui/`. Keep the prototype's class names so its CSS applies. Static files (logo, fonts) go under `public/assets/`.
3. **Portal shell task** (`portal-shell`). Build it once; every component depends on it.
   - **Personas** (`lib/demo/`): the Blueprint's personas (id, name, email, role, organisation, audience, initials), the demo data seeded from the prototype, and a fixed demonstration date so the story never drifts.
   - **Sessions:** `POST /api/session` takes an email and any password, accepts only the personas' demo emails, and sets an httpOnly, SameSite=Lax cookie holding the persona id and an HMAC-SHA256 signature made with Web Crypto (it must work in the proxy's edge runtime and in Node). Sign with `DEMO_SESSION_SECRET` when set; otherwise with a key derived from `SITECORE_EDITING_SECRET` and a fixed prefix (`demo-session:`), so the head needs no new secret. `DELETE /api/session` signs out. Never put either secret in the repository or the client bundle.
   - **Sign-in gate** in `src/proxy.ts`, before the Content SDK proxy chain: let Page builder and preview through (the `__prerender_bypass` cookie, or an `sc_itemid` parameter), let `/sign-in` through (redirect a signed-in visitor to `/`), and send everyone else without a valid session to `/sign-in?next=<path>`. Add `assets/` to the proxy `matcher`'s exclusions, or the logo and fonts on the sign-in page redirect to it too.
   - **Personalization by role:** in the `PersonalizeProxy` config, `getExtraUtmParams` reads the session cookie and returns `{ campaign: <persona's audience> }`. Page builder audiences match on it.
   - **Shell:** `src/Layout.tsx` wraps `headless-main` in the portal's sidebar (navigation from the persona's `navigation`, in order), header (breadcrumb, profile menu with Sign out) and footer (Reset demo). `src/Layout.tsx` is also imported by the client `global-error` page, so it must not import `next/headers`: read the cookie in `src/app/[site]/[locale]/[[...path]]/page.tsx` (not in draft mode) and pass the persona to `Layout` as a prop. The sign-in page (`bare` in the Blueprint) renders without the shell. In Page builder and preview, show the default persona with a "Previewing as" tag, and disable Sign out and Reset demo.
   - **Demo data service:** `GET /api/demo` returns the signed-in persona's view (their records, tasks and counts; the default persona when signed out); `POST /api/demo` runs one action per journey the Blueprint names (`submitClaim`, `payInvoice`…) and `reset`, and requires a session. Keep the state in a private Vercel Blob (`@vercel/blob`, `access: 'private'`, read with `get`, written with `put` and `allowOverwrite`) when `BLOB_READ_WRITE_TOKEN` is set, and in memory otherwise (local runs). Validate every action's input on the server.
   - **Client store:** one `useDemo()` hook (`useSyncExternalStore` over a fetch of `/api/demo`), `act(action)` that posts and updates it, a toast, and the shared drawer for record details.
   - List `DEMO_SESSION_SECRET` and `BLOB_READ_WRITE_TOKEN` in `.env.remote.example` (names and a comment, never values).
4. **Component tasks:** for `{name}`, read the prototype's component and the files it imports, then write the Content SDK component under `components/portal/`:
   - Every word, link and image in the model contract's `fields` comes from a field and renders with the SDK's field components (`Text`, `RichText`, `Image`, `Link`), so it edits inline. Never hard-code copy that belongs in a field. Fill tokens (`{firstName}`, `{district}`) from the persona, except in Page builder, where the raw field must stay editable.
   - Records come from `useDemo()` and actions go through `act()`. A component that calls a hook starts with `'use client'`, or the page answers 500 even though the build is green.
   - Until the persona's data has loaded, render a quiet placeholder: never a default persona's numbers, which flash on screen for the wrong person. Don't copy loaded data into `useState`'s initial value; derive it, and keep only what the person changed in state (a form's contact details follow the persona until edited).
   - Link fields can be absent: pass `field ?? { value: {} }` and show the link only when it has an `href` (or in Page builder).
   - **A container with dynamic placeholders** (the dashboard's columns) renders each one with `AppPlaceholder` and the server component map: `import componentMap from '.sitecore/component-map'`, `<AppPlaceholder name={\`dashboard-main-${params.DynamicPlaceholderId ?? '1'}\`} rendering={rendering} page={page} componentMap={componentMap} />`. The client `Placeholder` there shows "missing React implementation" for server components.
   - Copy the prototype's markup and CSS classes; empty states, loading states and disabled actions in Page builder are part of the component.
5. `sandbox.exec.content-sdk-cli` with `generate-map`. Never edit the generated component map by hand; its key must equal the rendering name.
6. `sandbox.exec.build`. Fix what fails and build again until it is green. Never commit a red build.
7. `sandbox.git.commit` to your branch, then submit with the commit SHA and the files you added.

Change only your task's own files. The shell's files (`src/Layout.tsx`, `src/proxy.ts`, `lib/demo/`, `components/ui/`) belong to the shell task: a component task that needs something new there stops with `needs_decision`.

**No repository.** When `repo-inventory` says `"source": "live-site"`, read each component's markup with `browser.page.markup` (its `url` and `selector`) and its values with `browser.page.styles`; `browser.screenshot` to compare. Never call `github` tools on such a project.
