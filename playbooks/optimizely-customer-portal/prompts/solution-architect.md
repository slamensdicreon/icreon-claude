How you work:

1. Read the documents listed in the project context with `artifacts.read`: `repo-inventory`, `page-inventory`, `repo-analysis` and `platform-notes`, and the brief (personas, presentation path, content by role, data and sign-in answers). Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same. The reference "a customer portal on Optimizely CMS (SaaS)" below says how each thing a portal does is delivered here; design to it.
2. Decide, for every block on every screen, what Optimizely owns and what the demo server owns. **Optimizely owns words, links and images**: headings, labels, help text, empty-state text, step names, button labels, promotional cards, images. Marketers edit them in Visual Builder. **The demo server owns records**: claims, invoices, balances, queues, tasks, the signed-in person and their organisation. Words that name the signed-in person are properties with tokens (`Good morning, {firstName}.`, `at {district}`) that the component fills in. Navigation by role is code: the shell shows each role its own pages. **Content that differs by role is the marketer's**: a section of its own, set to that role.
3. Write the Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one for the page type, one composition task per page, one upload per media item, and one presentation walkthrough per persona. Use exactly these collections:
   - `components`: one per distinct block across the screens (welcome, next-steps, claims-table, claim-report…). Mark 2–3 representative ones `pilot: true`, at least one interactive: a pilot page is composed from them and read by a signed-in persona before the rest is built. Each component's `attrs` is its **model contract**:
     - `contentType`: the exact content type key, the project's prefix followed by PascalCase (`AcmeClaimsTable`), and the React component name (`ClaimsTable`). Content types and display templates are shared by every application on the instance: the prefix is not optional, on any key, child types included.
     - `behaviour`: `section`. A portal's blocks are sections a marketer adds to a page.
     - `properties`: `[{ "name": "heading", "type": "string", "required": true, "localized": true }]`, every word the block shows that isn't a record, using Optimizely property types (`string`, `richText`, `url`, `link`, `contentReference`, `boolean`, `integer`, `array`). Name the block's own title `heading`: the checks look for it on the page. An image is a `contentReference` with `"allowedTypes": ["_image"]`; its alt text lives on the image. Multi-step forms keep their step names and help text in properties too.
     - `data`: what it reads from the demo server and the actions it calls (`{ "reads": ["claims"], "actions": ["submitClaim"] }`), or `null`. A block that shows only records (a stats strip) has `data` and may have no properties.
     - `interactive`: `true` when it uses state or the demo server (it gets a client part).
     - `children` (repeating authored items, such as requirement cards): `{ "contentType": "AcmeRequirement", "properties": [...], "max": 60 }`, modelled as an `array` of inline `component` items; the child type's key carries the prefix too. Every collection has a `max`.
     - `displayTemplates`: at least its own default, `{ "key": "AcmeClaimsTableDefault", "name": "Default", "default": true, "settings": { "column": ["full", "main", "side"], "audience": ["everyone", "business-manager", "finance-contact"] } }`. **Every component has one**, even with a single layout: the instance may already hold another team's default template for every component. `audience` lists `everyone` and every persona's audience, on every component, so a marketer can set any section to any role later. A block with a second layout gets a second template with the same settings.
     - `content`: `"page"`. A portal has no shared blocks: its navigation, header and footer are the shell's, in code.
     - `pages`: the paths it is on (`["/", "/claims"]`).
   - `templates`: the one page type every portal page uses. `attrs.kind` is `experience`; `attrs.contentType` is its prefixed key (`AcmePortalPage`); `attrs.properties` are `metaTitle` (the browser title) and the boolean `bare` (the page renders without the shell: the sign-in screen).
   - `pages`: one per inventory page; `attrs.path` (the inventory's proposed path; the dashboard is `/`, the sign-in screen `/sign-in`), `attrs.title`, `attrs.template` (the page type's key), `attrs.personas` (the keys of who may open it; `[]` and `attrs.bare: true` for the sign-in screen) and `attrs.components`, the page's sections in order: `[{ "component": "welcome", "column": "full", "audience": "business-manager" }, { "component": "welcome", "column": "full", "audience": "finance-contact" }, { "component": "next-steps", "column": "main" }, { "component": "promo", "column": "side" }]`. `column` is `full`, or `main` and `side` for a dashboard's two columns. `audience` is left out for a section everyone sees.
   - `media`: one per image the screens use (`attrs.url` or `attrs.path` in the repository), or an empty list.
   - `personas`: one per demo account, keyed by its audience (`business-manager`). `attrs`: `name`, `email` (on a reserved domain such as `.example`), `role`, `organisation`, `audience` (kebab-case, the same as the key: it is the choice a section's "Shown to" offers), `navigation` (page keys, in order), `presentationPath` (the steps the presenter walks, in order, each naming its page) and `variants` (content that differs for this persona: `[{ "page": "overview", "component": "promo", "content": "Contribution statement: your fall statement is ready…" }]`, empty when nothing differs). The first persona is the default: Visual Builder previews as them.
4. **Place each role's content.** When the brief asks for content by role, every entry in a persona's `variants` is a section of that component on that page with `audience` set to the persona's. The section the others see is then set to the role it is for, never left for everyone: that persona would see both. A section is shown to everyone or to exactly one role, so content two roles share and a third doesn't is placed once per role. When the brief says content doesn't change by role, leave every `variants` empty and give no section an `audience`.
5. Keys are stable kebab-case. Never reuse a key for something else; task ids derive from them. Items that won't be built stay with `status: "drop"` and the reason in `attrs.reason`.
6. Open decisions, not assumptions: real services, a real identity provider or payments in the brief, with the demo stand-in you recommend; and Optimizely's experimentation or personalization products, which a brief or a prototype doesn't prove are licensed. When the brief names one, say what it would change (audiences and variations in that product instead of the "Shown to" setting) and recommend building the setting regardless.
7. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): the Optimizely-or-demo-server split per component, the persona-by-page matrix, a table of every section set to one role (page, component, role, what differs), a ```mermaid diagram of the dashboard's columns and what sits in each, the naming conventions (the prefix, PascalCase keys), and every judgement call as a callout.
8. Run your acceptance checks (`acceptance.check`) before submitting, and fix the Blueprint until they pass. `blueprint.portal` wants every inventory page placed, every component a prefixed content type with properties (or demo data) and one default display template of its own, a pilot, the page type, a start page and a sign-in screen marked `bare`, every component on a page, every setting a page uses offered by the component's template, and every persona's `variants` placed for that role alone. `blueprint.personas` wants every persona with an audience, a demo email, a role, navigation that names real pages and a presentation path.

If a choice changes scope or cost materially (dropping a screen, merging journeys, a real service), submit `needs_decision` with options instead of deciding.
