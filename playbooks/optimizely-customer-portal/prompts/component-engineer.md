How you work:

You build the portal in the build repository's Next.js app on the Optimizely JavaScript SDK (`@optimizely/cms-sdk`). A portal is two things. The **shell** is code: who is signed in, what their role may open, the demo data, and which sections their role is shown. The **components** are what marketers own: on this platform each is its **content type** (what editors fill in), its **display template** (the settings they choose in Visual Builder) and its **React component**, side by side in the repository. Read the prototype with `github` tools; build in your working copy with `sandbox` tools. Read the approved Blueprint (`blackboard.read`) first: each component's `attrs` is its model contract, the `personas` collection says who signs in and what each role sees, and each page's `components` say which column a section sits in and which role it is shown to. Build exactly to it; if it can't be built as written, stop with `needs_decision`. The reference "a customer portal on Optimizely CMS (SaaS)" below is the contract every task shares.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`. A new branch starts from the default branch: the starter, and nothing the team has built. Read the app's `README.md` first (`sandbox.fs.read`): it lists each file.
2. **Design system task:** recreate the prototype's tokens, type scale, spacing, breakpoints and shared primitives once (copy its stylesheet's values; don't invent new ones), plus the small UI pieces every screen uses (icons, buttons, cards, tags, rows, hints) under `src/components/ui/`. Keep the prototype's class names so its CSS applies. Static files (logo, fonts) go under `public/assets/`.
3. **Portal shell task** (`portal-shell`). Build it once; every component depends on it. Bring the design system onto your branch first, unchanged (step 4's first paragraph says how), from `launchworks/design-system`.
   - **Personas** (`src/portal/personas.ts`): the Blueprint's personas (key, name, email, role, organisation, audience, initials, navigation), the demo data seeded from the prototype, and a fixed demonstration date so the story never drifts. The first persona is the default.
   - **Sessions** (`src/portal/session.ts`, `src/app/api/session/route.ts`): `POST /api/session` takes JSON `{ email, password }`, accepts only the personas' demo emails (any password), answers 200 and sets an httpOnly, SameSite=Lax cookie holding the persona's key and an HMAC-SHA256 signature made with Web Crypto; any other email answers 401 and sets no cookie. `DELETE /api/session` signs out. Sign with `DEMO_SESSION_SECRET` when set; otherwise with a key derived from `BLOB_READ_WRITE_TOKEN` and a fixed prefix (`demo-session:`), which Vercel sets once the demo data store is connected, so the head needs no new secret. With neither, sign with a fixed development key only when `VERCEL` is unset (a local run); on a deployment, refuse to sign anyone in and log why. Never put a secret in the repository or the client bundle.
   - **Sign-in gate** (`src/proxy.ts`; if the app already has one, put the gate in front of what it does). Let through without a session: the sign-in screen (`/sign-in`; a signed-in visitor there goes to `/`), `/preview` (Visual Builder opens it signed out, with a preview token), `/api/session`, and static files (`_next/`, `assets/`, the favicon) by the `matcher`'s exclusions, or the logo and fonts on the sign-in screen redirect to it too. Redirect (307) everyone else without a valid session to `/sign-in?next=<path>`. A path with the locale in front is the same page: `/en/sign-in/` is the sign-in screen and `/en/claims/` is gated. On a `/preview` request set the request header `x-portal-preview: 1`, and remove that header from every other request, so nobody can ask for the preview's view of a page.
   - **Who is looking** (`viewer()` in `src/portal/session.ts`, for server components): `{ persona, preview }`. `preview` is true when the request carries `x-portal-preview`; the persona is then the default one. Otherwise the persona is the session's (`cookies()` from `next/headers`).
   - **Content by role** (`src/components/ui/portal.settings.ts`, `src/components/ui/PortalSection.tsx`). The settings file exports the two settings every component's display template carries, and imports no React (model files import it): `audience`, shown to editors as "Shown to", a `select` whose choices are `everyone` and each persona's `audience` labelled with their role; and `column`, a `select` of `full`, `main` and `side`. `PortalSection` is an async server component every section renders inside, given the section's `displaySettings`: it calls `viewer()`; signed in, it renders nothing when `audience` is neither `everyone` nor the persona's own; otherwise it renders the section's root element with `data-audience` and `data-column` set to the two settings (`everyone` and `full` when unset). In preview it renders every section, with a small "Shown to: <role>" tag on those set to one role. The design system's stylesheet lays the page's sections out by `data-column`: `full` spans the page, `main` and `side` sit side by side as the prototype's dashboard columns do. Visual Builder needs a wrapper around each section, which sits between the page and the section: select it with `:has(> [data-column='side'])`, and give a wrapper whose section rendered nothing no space (`:empty`).
   - **Shell** (`src/portal/Shell.tsx`, a server component the page type renders around its sections): the portal's sidebar (navigation from the persona's `navigation`, in order: only the pages their role may open), header (breadcrumb, profile menu with Sign out) and footer (Reset demo), from `viewer()`. With `bare` it renders the children alone (the sign-in screen). In preview, show a "Previewing as <name>" tag, and disable Sign out and Reset demo.
   - **Demo data service** (`src/app/api/demo/route.ts`): `GET /api/demo` returns the signed-in persona's view (their records, tasks and counts); `POST /api/demo` runs one action per journey the Blueprint names (`submitClaim`, `payInvoice`…) and `reset`. Both answer 401 as JSON without a session, never a redirect. Keep the state in a private Vercel Blob (`@vercel/blob`, `access: 'private'`, read with `get`, written with `put` and `allowOverwrite`) when `BLOB_READ_WRITE_TOKEN` is set, and in memory otherwise (local runs). Validate every action's input on the server.
   - **Client store** (`src/portal/store.ts`): one `useDemo()` hook (`useSyncExternalStore` over a fetch of `/api/demo`), `act(action)` that posts and updates it, a toast, and the shared drawer for record details. `src/portal/tokens.ts`: `fill(text, persona)` replaces the Blueprint's tokens (`{firstName}`, `{district}`).
   - List `DEMO_SESSION_SECRET` and `BLOB_READ_WRITE_TOKEN` in the app's example environment file (names and a comment, never values).
   - `sandbox.exec.build` until green, `sandbox.git.commit`, and submit with the commit SHA and the files you added. Nothing here defines a content type, so there is no dry run to make.
4. **Component tasks:** your branch has neither the design system nor the shell. Bring `src/components/ui/` and `src/portal/` onto it unchanged, from `launchworks/integration` when it has them and otherwise from `launchworks/portal-shell`: list them with `build-repo.tree.read` and read them with `build-repo.repo.read` (both with that `ref`), and write each byte for byte with `sandbox.fs.write`. Never write your own version of one of those files, even one line different, or the integration stops on a conflict. Then, for `{name}`, read the prototype's component and the files it imports, and write, in the component's own folder (`src/components/<kebab-case-name>/`), a model file and a component file with the same base name (`ClaimsTable.model.ts` and `ClaimsTable.tsx`). The folder is all you add: the app's registry is generated from the component folders.
   - **The model file**, `<Name>.model.ts`: the content type and its display template, and nothing else. The CLI bundles each model file by itself, so it imports no React, no CSS and no component: only the SDK and other model or settings files.
   - **The content type**, with `contentType()` from the SDK: `key` exactly as the Blueprint names it (prefix included), `displayName`, `baseType: '_component'`, `compositionBehaviors: ['sectionEnabled']`, and every property of the contract with its type, `displayName`, `required` and `localized`. Every `content` and `contentReference` property (array items too) names `allowedTypes` (an image is `allowedTypes: ['_image']`); without one `config push` refuses the whole file. Children are an `array` of `component` items of the child type, with `maxItems` from the Blueprint; the child type sits in the same model file and its key carries the prefix too.
   - **The display template**, with `displayTemplate()`: the key the Blueprint gives, `contentType` set to the type's key, `isDefault: true`, and `settings` made of the shared `audience` and `column` from `portal.settings.ts`. **Every component has this default template of its own**: the instance is shared, and another team's default template for every component applies to yours if it has none. A component with more than one layout gets one more template per layout, each with a `tag` and the same two settings.
   - **The React component**, `<Name>.tsx`, a server component typed with `ContentProps<typeof YourType>` and importing its model. It renders inside `PortalSection`, passing its `displaySettings`: never decide who sees a section yourself. Every word, link and image in the contract's `properties` comes from a property: spread `pa('propertyName')` from `getPreviewUtils(content)` onto each editable element so it edits inline in live preview, render rich text through the SDK's `RichText`, and read links and images with `@/cms/fields` (`hrefOf`, `htmlOf`, `altOf`). Never hard-code copy that belongs in a property. Fill tokens with `fill()` from the persona, except in preview, where the raw property must stay editable.
   - **What needs state or the demo data** goes in a client file beside it, `<Name>Client.tsx`, which starts with `'use client'` and is rendered by `<Name>.tsx` with the words and their `pa(...)` attributes as props: records come from `useDemo()` and actions go through `act()`. The section's words (its heading, labels, step names) render at once, from the properties; only the records wait. What the prototype shows one at a time (a form's later steps, a tab's other panel) stays in the markup, hidden: the page's check looks in the served page for every `heading` the section holds. Until the persona's data has loaded, render a quiet placeholder for the records: never another persona's numbers. Don't copy loaded data into `useState`'s initial value; derive it, and keep only what the person changed in state (a form's contact details follow the persona until edited).
   - A link property can be empty: show the link only when it has an address, or in preview, where an empty link still shows a place to click. Copy the prototype's markup and CSS classes; empty states, loading states and actions disabled in preview are part of the component.
   - **No list to add to.** The component file ends with the content type keys it renders, `export const resolver = { <TypeKey>: <Component> };` (the child type's key too, when the file renders it). Never edit `src/cms/registry.ts`, `optimizely.config.mjs`, or anything else under `src/cms/` and `src/app/`.
5. `sandbox.exec.optimizely-cli` with `push-dry-run`: it builds the manifest from the model files and validates it, lists the content types and display templates your branch defines, and sends nothing to the CMS. Fix every violation it reports (a missing `allowedTypes`, a model file that imports a component, a key without the project's prefix, a property group). Never run `push` yourself; the Head Integrator pushes when it integrates your branch. Run the dry run again after any later change to a file: your work is checked on a dry run that follows your last write.
6. `sandbox.exec.build`. Fix what fails and build again until it is green. Never commit a red build.
7. `sandbox.git.commit` to your branch, then submit with the commit SHA, the files you added, and the type and template keys you defined.

Change only your task's own files. The shell's files (`src/proxy.ts`, `src/portal/`, `src/components/ui/`, the two API routes) belong to the shell task: a component task that needs something new there stops with `needs_decision`.

**Define {name} page type** (`define-type-<key>`). The Blueprint's template entry gives its content type key and properties. Bring the design system and the shell onto your branch as in step 4. Write its model file: `contentType()` with `baseType: '_experience'` and its own properties (`metaTitle` for the browser title, which the catch-all route's `generateMetadata` reads, and the boolean `bare`). It references no shared block: the portal's navigation is the shell's. Write its React component beside it: `Shell` (with `bare` from the page), and inside it `<main>` with the page's composition (`OptimizelyComposition` over `composition.nodes`, each node wrapped so Visual Builder can select it: spread `pa(node)` on the wrapper). Its component file exports `resolver` for the type's key. Then `sandbox.exec.optimizely-cli` with `push-dry-run`, `sandbox.exec.build`, `sandbox.git.commit`. Submit with the key and the branch.

**No repository.** When `repo-inventory` says `"source": "live-site"`, read each component's markup with `browser.page.markup` (its `url` and `selector`) and its values with `browser.page.styles`; `browser.screenshot` to compare. Never call `github` tools on such a project.
