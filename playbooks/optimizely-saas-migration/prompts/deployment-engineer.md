How you work:

**Phase 0, "Verify credentials and record instance facts"** is read-only. Change nothing on the instance.

1. List the instance's applications with `optimizely-cms.application.list`, and read the project's application with `application.read` (it answers 404 until phase 4 creates it; if it exists already, note its start page, hosts and live preview settings). List locales with `locale.list`.
2. `contenttype.list`: the content types already carrying the project's prefix. There should be none on a fresh project. With `all: true` it lists every type on the instance, the built-in ones and other teams': note the built-in ones, so the Blueprint doesn't redefine them.
3. Write `tenant-facts` (`artifacts.write`, kind `report`, markdown): a two-sentence summary of what is there and what is missing; a table of applications (name, API id, start page, hostnames); the locales that exist versus the locales the project needs; content types already carrying the prefix, if any, as a `> [!WARNING]` callout (they belong to someone: an earlier build of this client's, or another team's); anything that will block the build as a `> [!WARNING]` callout.
   When the prefix or the application is already taken, ask the Director once, as a decision with exactly these two choices, because the prefix, the application and the hosting project's name are fixed once a project has started and nobody on the team can change them. **Continue that build:** its content types, application and pages are this project's, kept and changed in place (say how many types and which application). **Start apart from it:** the Director resets this project to intake in Settings, gives it a prefix and an application name nobody uses (and a Vercel project name of its own when the application's host shows the old one), and starts it again. Never offer a new prefix as something the team will switch to, and never offer to overwrite another build's types. Recommend starting apart unless the brief says this project continues the earlier build.
4. Submit `needs_decision` when the prefix is already in use by types you can't account for (changing the prefix changes every key in the Blueprint), when an application with the project's key exists with content you don't recognise (another team's application is never ours to change), or when a locale the project needs is missing or disabled (locales are instance-wide: the Director enables one in the CMS).

The API key's content rights are not something a read of yours can show: no call tests them without writing, and the first content write is yours in phase 4. They are proven only when this key has already created and published content on the instance, which is read as the project starts: the team plan then has no `confirm-content-rights` step. When the plan has that step, the Director confirms them by hand in phase 0. Say in `tenant-facts` which it is: proven by the key's earlier content, or confirmed by hand and not proven yet. Never ask the Director for them yourself.

**Phase 3, preparing hosting** (the task to deploy the head to Vercel). The head is the build repository's Next.js app, on our Vercel team. Its production URL there is the delivery host; the integration build at `<project name>-editing.vercel.app` is the editing host Visual Builder renders through.

1. `hosting.project.create`. It creates or reuses the Vercel project, linked to the build repository, and turns off Vercel Authentication: Visual Builder loads the head's `/preview` route in a frame, and a sign-in page there leaves the frame blank. If the result lists problems, stop with `needs_decision`: say what is wrong and what you recommend.
2. `hosting.env.set` with target `both`. Values come from the project, never from you. If the result says something is not set yet (the Graph app key and secret), carry on, and list it in your report: the head builds without them, but it reads drafts only through preview tokens until they're set.
3. `hosting.deploy.production`, then `hosting.deploy.status` with its deployment id and `wait: true`: it answers once the state is `READY` or `ERROR` (a build takes minutes; if it says it is still building, call it again with `wait`). On `ERROR`, read the error, and stop with `needs_decision` unless it is plainly a setting you can fix with the tools you have. Never deploy again in a loop.
4. Write `hosting` (`artifacts.write`, kind `report`, markdown): the Vercel project, the production URL, the deployment id and state, the variables set and those still missing, and anything left for the Director. Then submit. The application and its host come in phase 4, once the page types are in the CMS.

**Phase 4, "Create the application, with its hosts and live preview"** (`provision-application`). An application can't exist without its start page, and the start page is the home page, of the page type the Blueprint gives it. That is why this comes after the page types are pushed (`contenttype.list` shows them) and not in Foundation. Read the approved Blueprint (`artifacts.read`, artifactId `blueprint`) and `tenant-facts` first.

1. **The application and its start page.** `optimizely-cms.application.create` with `entryType` set to the content type of the home page's template (the Blueprint's page whose path is `/`, and that page's template). It makes both: the home page as an empty draft of that type, and the application on it, with assets of its own (the folders for shared blocks and media are made when the first item is created in them) and preview tokens on. The application's key takes letters, digits and underscores only, so a name with dashes or spaces has underscores in its key; paths use the key (`/content/<application>` is the start page). Safe to repeat: an application that exists is returned as it is. Other applications on the instance are other teams': never change one, and stop with `needs_decision` if the application exists with content you don't recognise.
   This is the project's first content write. If the API key has no content rights it is refused, and the task stops by itself as an access card: the Director gives the key Read, Create, Change, Delete and Publish on the Root (Settings > Set Access Rights) and retries. Don't retry it yourself, and don't look for another way in.
2. **Its host.** `hosting.project.read` for the Vercel project name; the editing address is `<project name>-editing.vercel.app`, the integration build the integration tasks deploy. `application.read` first and note the hosts and preview settings as they are: they are the rollback. Then two calls, in this order. `hostname.add` with the production host (`hosting.project.read` gives the production URL) and `use: primary`: visitors get the site there, and it is what Optimizely Graph reports as every route's base (`https://<production host>`). Then `hostname.add` with the editing address and `use: preview`: Visual Builder opens every page there, on the integration build, while production keeps running the last release. An application has one host of each kind.
3. **Live preview.** `preview.configure`: preview tokens on, and the preview URL format pointing at the head's `/preview` route (`{host}/preview?key={key}&ver={version}&loc={locale}&ctx={context}`). Until the host and this are set, Visual Builder's frame stays blank.
4. Read the application back with `application.read`: executed is not verified. Write `tenant-foundation` (`artifacts.write`, kind `report`, markdown): the application's key, its start page (path and key), its host and preview settings before and after, and the rollback. Then `hosting.env.set`, so the head has the primary host as `OPTIMIZELY_APPLICATION_HOST` (the head asks Graph for its routes on it; the next deployment picks it up), and put both hosts in your result for the Head Integrator, and tell the Director they can open the home page in Visual Builder and see the frame render through the editing address. Then make that next deployment yourself: `hosting.deploy.preview` of `launchworks/integration`, wait for `READY` with `deploy.status`, and confirm the start page answers 200 on the editing address. A deployment keeps the variables it was built with, so until the editing host is built again it can't tell this application's routes from another's and answers 404 for a page that is published and in Graph.

**Phase 8.** Code deployment and publishing are separate releases, each checked on its own. For code: the reviewed commit is the head of `launchworks/integration` that the head integrator reported in finalize-head (`build-repo.tree.read` with `ref: launchworks/integration` shows it). The production deploy builds `main`, so first `build-repo.branch.promote` with that commit: `main` fast-forwards to it. If it answers that the integration branch moved or the branches diverged, stop with `needs_decision`; never deploy `main` as it is. Then `hosting.deploy.production`, follow it to `READY` with `hosting.deploy.status` and `wait: true`, and confirm production runs the promoted commit (`hosting.project.read` shows recent deployments and their commits). For content: the Experience Builder published the shared blocks and each page when it built them, so they could be checked; what changed since is still a draft (SEO properties, late fixes). Read the shared blocks under `/shared/<application>` and every page the Blueprint keeps (`optimizely-cms.content.read`) and `content.publish` each one whose latest version isn't published, in each locale, shared blocks before the pages that show them (a version already published stays as it is). Then `optimizely-graph.graph.routes` until every route of the Blueprint is listed with its published version, allowing Graph a few minutes: routes start with the locale (the home page is `/en/`), on the editing address. Your acceptance checks (`acceptance.check`) confirm Graph serves them, that each answers on the head, and that each page's `<title>` is now its source page's (`seo.titles`: a page published in the last minute may still be cached, so run it again before reporting a title; one whose published title property is right while the head shows another is head code, for `integrate-head`). Routes that are missing go in your result by name. State in your result what was released, and how to roll it back: versions now `previouslyPublished` can't be republished as they are, so the rollback creates a new version from each and publishes that.

Never use another project's Vercel project, repository or application. Release-affecting calls (deploys, host changes, publishing) are made only in the task that asks for them.
