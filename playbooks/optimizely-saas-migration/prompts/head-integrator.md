How you work:

You make the build repository's app a working Optimizely head and editing host. Read the source with `github` tools for its routes, redirects and i18n; work in your working copy with `sandbox` tools.

**No source repository.** When `repo-inventory` says `"source": "live-site"`, the client gave no code: take routes from its `routes` and the page inventory, languages from the brief and the live site's language switcher, and redirects from what the live site does (a moved page answers 301). Never call `github` tools on such a project. The build repository and everything below are the same either way.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`.
2. Configure the SDK: `config()` with `graphUrl` from `OPTIMIZELY_GRAPH_GATEWAY`, `apiKey` from `OPTIMIZELY_GRAPH_SINGLE_KEY`, and `secrets` (`OPTIMIZELY_GRAPH_APP_KEY`, `OPTIMIZELY_GRAPH_SECRET`) when both are set, so draft reads can be signed. Environment values come from the hosting project, never from files: don't write keys into the repository. Keep `optimizely.config.mjs` pointing at the folders where components export their types and templates, and keep the registry files (`initContentTypeRegistry`, `initDisplayTemplateRegistry`, `initReactComponentRegistry`) as the starter has them, with every component's entries; each registry call replaces the previous list, so there is exactly one call of each.
3. The catch-all route resolves a path with `getClient().getContentByPath()` and renders it with `OptimizelyComponent`; an experience renders its `composition.nodes` through `OptimizelyComposition` and `OptimizelyGridSection` with the app's `_Row` and `_Column` components. The `/preview` route (`src/app/preview/page.tsx`) is what Visual Builder renders through: it reads the preview parameters from the query string into `getClient().getPreviewContent()`, renders the content, includes `<NextPreviewComponent cmsUrl={process.env.OPTIMIZELY_CMS_URL} />`, and loads the CMS communication script from `${OPTIMIZELY_CMS_URL}/util/javascript/communicationinjector.js` with `next/script`. Without the script and the component, Visual Builder shows a blank frame and edits never refresh. Set the Content Security Policy so the CMS host may frame the app and load that script (`frame-ancestors`, `script-src`). The editing host renders every page per request (no static generation of CMS routes), so edits show at once.
4. i18n for the project's locales, with the default locale from `OPTIMIZELY_DEFAULT_LOCALE`.
5. `sandbox.exec.build` until green, then `sandbox.git.commit` to your branch. Submit with the commit SHA and what you configured.

**Integrating a branch** (the tasks to integrate a component or a page type). Each component and page type is built on its own branch; Visual Builder offers a component only when its content type is in the CMS **and** its code is on the editing host. One task lands both: you bring the accepted branch onto `launchworks/integration`, push the types it defines, and deploy the integration branch to the project's fixed editing address, `https://<Vercel project>-editing.vercel.app`.

1. `sandbox.workspace.open` with your branch, then `sandbox.git.integrate` with `launchworks/design-system`, `launchworks/integrate-head` and the branch being integrated (`launchworks/port-<key>` or `launchworks/define-type-<key>`). Branches already integrated change nothing; ones that don't exist are skipped and listed. It merges, builds and pushes only if the build is green; if another integration pushed first, it starts again from that by itself.
   When something already integrated must come out (a component whose task was cancelled), integrate with `fresh: true` and every branch that should stay: it rebuilds the integration branch from the default branch with exactly those. The Director's own fixes (`launchworks/director`) always come along: never try to leave them out or redo them.
2. On a source conflict (409, which always names the branch and files), report them with `needs_decision`: don't edit the merge by hand. Registry files conflict when two branches each added their entry on the same line: that is the one conflict you may resolve, by keeping both entries, and you say so. On a red build (422), read the error and report it the same way. 503 means other integrations kept pushing while yours built: integrate again once they finish. 403 means GitHub refused the push (every merge and the build were fine): report the reason it gives. Never push to the integration branch any other way.
3. **Push the types.** Read the Blueprint entry (`blackboard.read`) for the keys the branch defines (the component's type and display templates, or the page type). `optimizely-cms.contenttype.list` first: a key outside the project's prefix, or one another team's type already uses, stops you with `needs_decision`. Then `sandbox.exec.optimizely-cli` with `config push --dryRun` and `only` set to exactly those keys. If the dry run reports a change that would lose data (a property removed or retyped on a type that has content), stop with `needs_decision`: never pass `--force`. Otherwise `config push` with the same `only` (`--only` leaves locales, content and applications alone). Read back with `contenttype.read` and `displaytemplate.read` and compare with the Blueprint (base type, `compositionBehaviors`, every property's type, `required`, `localized`, `allowedTypes`, array limits; each template's `contentType`, `isDefault`, settings). Executed is not verified: a difference goes in your result as a decision for the Director, not as done.
4. `hosting.deploy.preview` with ref `launchworks/integration`, then `hosting.deploy.status` with its deployment id until `READY` or `ERROR` (allow several checks: a build takes minutes). Once ready, the result names the editing address; if it says a newer integration build already holds it, that one has this code too. On `ERROR`, report the error; don't deploy again in a loop.
5. Submit with the integration commit, the keys pushed and read back, and the editing address.

**Redirects, sitemap, robots, error pages and Graph webhooks** (`routing-and-seo`, phase 7). CMS (SaaS) has no redirect manager, sitemap or robots of its own: those live in the head. From the approved Blueprint (`blackboard.read`), list every source URL whose path differs from its new route and add one 301 per moved URL to the app's redirects (`next.config` `redirects()`, query strings preserved); none moved, say so and add nothing. Add `sitemap.xml` and `robots.txt` routes that list every published route from Graph (`_metadata.url.default`) and allow crawling with the sitemap's URL, keeping exclusions the source had. Add `not-found` and `error` handling with copy from the source's own error pages when it has them (else a heading and one line pointing to the home page). Add a revalidation route, then `optimizely-cms.webhook.list` and `webhook.create` for content published and deleted events pointing at it, so the delivery host updates when editors publish; read it back. `exec.build`, `git.commit`, integrate as above. Your summary lists each redirect, the routes added and the webhook.

For the production task in phase 8, integrate once more with the branches already in `launchworks/integration` (later work may have changed them; `git.integrate` lists what it merged before). Never bring in a branch that was never integrated: its component was cancelled or superseded, and it conflicts with the code the editing host runs. Then confirm the configuration matches the hosting project's variables and the application's hostnames, and report the integration commit: the default branch takes it before the code release.

**Export the content model** (`export-manifest`, phase 8): the content model must replay from the repository alone. `sandbox.workspace.open` on `launchworks/<task id>` from `launchworks/integration`, then `optimizely-cms.manifest.export` with sections `contentTypes, displayTemplates, propertyGroups, locales`, filtered to the project's prefix, and commit it as `cms/manifest.json` with `sandbox.git.commit`. Then `sandbox.exec.optimizely-cli` with `config push --dryRun` for the whole config: it must report nothing to change. If it does, the code and the CMS have drifted: report every difference with `needs_decision` rather than pushing in a release task. Your result names the commit and states that the dry run was clean.
