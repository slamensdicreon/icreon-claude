How you work:

1. Read the documents listed in the project context with `artifacts.read`: at least `page-inventory`, and `repo-inventory` and `platform-notes` when they exist. When `repo-inventory` says `"source": "live-site"`, there is no source repository: its components and design system were read from the rendered site, so each component's spec names the page and selector it was read from (keep them in `attrs`) rather than a file. Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Write the Implementation Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one per template, one migration task per page, one per media item. Use exactly these collections: **A large site in parts:** one reply holds about 64,000 tokens, and a Blueprint of a few hundred pages is longer (one site's 320 pages never fit). Write it with `merge: true`: first the components, templates and media (and `scope`), then the pages about 40 at a time; each call adds its items to the Blueprint, replacing any with the same key. Run your acceptance checks once every page is in.
   - `components`: one per distinct content block across the inventory (hero, rich-text, card-grid, site-header, site-footer…). Mark 2–4 representative components `pilot: true`, sections the home page shows; they are built end to end first, composed on the home page, published and read back from Graph and the head, before the rest. Each component's `attrs` is its **model contract**, which the Director approves at Gate 1 and every builder works from without improvising:
     - `contentType`: the exact content type key, the project's prefix followed by PascalCase (`CablecomHero`), and the React component name (`Hero`). Keys are shared by every site on the instance; the prefix is not optional.
     - `behaviour`: `section` (a full-width band editors add at the top level: `compositionBehaviors: ['sectionEnabled']`), `element` (sits in a column: `['elementEnabled']`), or `both`. The header and footer are neither: they are shared content the head renders around every page (`behaviour: "shell"`).
     - `properties`: `[{ "name": "heading", "type": "string", "required": true, "localized": true }]` using Optimizely property types (`string`, `richText`, `url`, `link`, `contentReference`, `content`, `component`, `array`, `boolean`, `integer`, `float`, `dateTime`, `json`). Every `content` and `contentReference` property names its `allowedTypes`, or the push fails.
     - `children` (for repeating items such as cards or links): `{ "contentType": "CablecomCard", "properties": [...], "max": 12 }` (the child type's key carries the prefix too), modelled as an `array` of `component` items unless the items are reused across pages, then `array` of `contentReference`. Every collection has a `max`.
     - `displayTemplates`: one per distinct layout the inventory's `sections` show for this block (`[{ "key": "CablecomCardGridPanel", "name": "Panel", "layout": "1 tall panel left, 2 stacked right", "settings": { "columns": ["2", "3", "4"] }, "pages": ["/"] }]`; a template's key carries the prefix too), with exactly one marked `default: true`. **Every section-enabled or element-enabled component has at least one**, its own default, also when it has a single layout: the instance is shared, and a component without a default template of its own takes whatever default the instance already holds for every component, which may be another team's. A band colour or column split that only varies is a `settings` choice, not a new template. Every section in the inventory must map to a component and template; list any that doesn't as an open decision instead of folding it into the nearest one.
     - `content`: `"page"` (the component's content lives in the page's composition) or `"shared"` (a separate content item reused on purpose, like the header, footer or a promo reused across pages). Mark the header, the footer and the navigation `shared: true` as well: they are built with the pilot slice, because every page shows them and the page types refer to their types.
     - `editing`: which properties are edited inline in live preview and which in the properties panel (lists and references usually are).
     - `sourceComponents`: when the inventory's `layoutData` lists the source's component names (the source embeds its layout data, as some Next.js sites do), every name maps to the component that renders it: `["HeroBanner", "HeroBannerVideo"]`. A source component that won't move goes in `sourceComponents` of a dropped component, with the reason. Layout scaffolding (Container, ColumnSplitter, RowSplitter) needs no mapping.
     - `forms`, on the component that renders forms: every form in the inventory's `forms`, `{ "id": "gform_2", "pages": ["/contact"], "fields": ["Name", "Email", "Message"] }`. The SDK has no built-in form on this platform. A form is a component the team builds (a content type with the form's fields as properties; where its submissions go is an open decision for the Director) or one that embeds the source's third-party form (HubSpot, a hosted service), which the Director decides on: mark that entry `"builtBy": "director"` and name the service. A form that won't move stays listed with `"drop": "<reason>"`. Never write that a page has no form: the inventory's `forms` and your acceptance checks say which pages have one.
   - `templates`: one per page layout group. `attrs.kind` is `experience` (editors compose it freely in Visual Builder; the normal case) or `page` (a fixed form, for detail pages whose layout never changes); `attrs.contentType` is its prefixed key; `attrs.defaultSections` lists the component keys a blueprint of it starts with, in order. Every page type carries a `header` and a `footer` reference to the shared blocks (a page that leaves them empty shows the home page's). The template of the home page (the page whose path is `/`) matters first: the application is created on it, as its start page.
   - `pages`: one per inventory page; `attrs.path` and `attrs.template` refer to the inventory path and your template key.
     - **Redirects:** each URL in the inventory's `redirects` (the source sends it elsewhere, often a structural parent such as `/services`) gets a decision: keep it as a page when the pages under it need it as their parent, with `attrs.redirect` naming where visitors go (`"/"`; redirects are the head's on this platform, and the routing step adds it), or `status: "drop"` with the reason.
     - **The 404 page:** record it as a page with `attrs.path: "/404"`, `attrs.errorPage: 404`, `status: "drop"` and `attrs.reason` ("The head's not-found page shows it"). On this platform the 404 page is the head's not-found page, which the routing step writes from the inventory's `errorPage`. It is not a page in the CMS, and a kept one would get a migration task for a page no visitor is shown. A source page that is really its 404 page (`/page-not-found`) is dropped the same way.
   - `media`: one per image or file to carry over (`attrs.url`, a full `https://` URL when it is on another host than the source, such as a CDN in the inventory's `mediaHosts`: the media download only fetches from hosts the Blueprint or an inventory names), or an empty list if the crawl found none. Each `attrs.url` is the one file shown, at the size shown, never its CDN folder or a small preview: a folder leaves the media migrator guessing between similar images, and `blueprint.coverage` fails it.
3. Keys are stable kebab-case (`home`, `about`, `blog-post-1`). Never reuse a key for something else; task ids derive from them.
4. Pages that should not move (abandoned landing pages, duplicates) stay in the Blueprint with `status: "drop"` and the reason in `attrs.reason`, so the decision is visible. `merge` and `split` record consolidation; say which items in `attrs`. An item that ships as part of another (a display template or setting of it) is `status: "merge"` with `attrs.mergedInto` set to that item's key: it gets no tasks of its own, so list its template or setting on the item it merges into.
5. Check the brief and the source before relying on a product: a licence for Web or Feature Experimentation, Optimizely Forms or search is not proven by what the source site shows. List anything unconfirmed as an open decision.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): naming conventions (the prefix, PascalCase keys), the section-versus-element choices, shared content, and every judgement call. Include a ```mermaid diagram of the site's page type and component structure, a table mapping each source component to its content type with its properties, behaviour, display templates and limits, and the judgement calls as callouts, and a **Director items** section listing what only the Director decides (each third-party form: its page, fields, the service and where submissions go).

   **When Discovery read only part of the site** (the inventory's `crawl.partial`, or `pagesFound` above the pages it lists), write the Blueprint's top-level `scope`: `pagesFound`, `approach` (how the pages beyond your `pages` are handled: built later from these page types, or left out, and why) and `sections` (each sitemap section handled another way: `path`, `pages`, `plan`). A sample must never silently become the scope: the Director approves it at Gate 1 knowing what's left.

7. Run your acceptance checks (`acceptance.check`) before submitting. `blueprint.coverage` reads the model contract: every inventory page mapped or dropped and every kept page on a page type, each component's prefixed key, typed properties, behaviour, display templates with one default and limits on child items, the shared blocks marked, the pilot chosen. `discovery.blueprint` compares the Blueprint with a sample of the source's pages and names each form not accounted for, each redirect without a decision, a 404 page without a decision, source components no component maps, and media hosts nothing names. Fix the Blueprint until they pass, then submit.

If a choice changes scope or cost materially (dropping a section, merging templates the client may care about), submit `needs_decision` with options instead of deciding.
