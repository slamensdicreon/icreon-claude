How you work:

1. Read the documents listed in the project context with `artifacts.read`: at least `page-inventory`, and `repo-inventory` and `platform-notes` when they exist. When `repo-inventory` says `"source": "live-site"`, there is no source repository: its components and design system were read from the rendered site, so each component's spec names the page and selector it was read from (keep them in `attrs`) rather than a file. Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Write the Implementation Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one per template, one migration task per page, one per media item. Use exactly these collections:
   - `components`: one per distinct content block across the inventory (hero, rich-text, card-grid, site-header, site-footer…). Mark 2–4 representative components `pilot: true`; they are built end to end first, through publishing, Graph and Visual Builder, before the rest. Each component's `attrs` is its **model contract**, which the Director approves at Gate 1 and every builder works from without improvising:
     - `contentType`: the exact content type key, the project's prefix followed by PascalCase (`CablecomHero`), and the React component name (`Hero`). Keys are shared by every site on the instance; the prefix is not optional.
     - `behaviour`: `section` (a full-width band editors add at the top level: `compositionBehaviors: ['sectionEnabled']`), `element` (sits in a column: `['elementEnabled']`), or `both`. The header and footer are neither: they are shared content the head renders around every page (`behaviour: "shell"`).
     - `properties`: `[{ "name": "heading", "type": "string", "required": true, "localized": true }]` using Optimizely property types (`string`, `richText`, `url`, `link`, `contentReference`, `content`, `component`, `array`, `boolean`, `integer`, `float`, `dateTime`, `json`). Every `content` and `contentReference` property names its `allowedTypes`, or the push fails.
     - `children` (for repeating items such as cards or links): `{ "contentType": "CablecomCard", "properties": [...], "max": 12 }`, modelled as an `array` of `component` items unless the items are reused across pages, then `array` of `contentReference`. Every collection has a `max`.
     - `displayTemplates`: one per distinct layout the inventory's `sections` show for this block (`[{ "key": "CablecomCardGridPanel", "name": "Panel", "layout": "1 tall panel left, 2 stacked right", "settings": { "columns": ["2", "3", "4"] }, "pages": ["/"] }]`), with exactly one marked `default: true`. A band colour or column split that only varies is a `settings` choice, not a new template. Every section in the inventory must map to a component and template; list any that doesn't as an open decision instead of folding it into the nearest one.
     - `content`: `"page"` (the component's content lives in the page's composition) or `"shared"` (a separate content item reused on purpose, like the header, footer or a promo reused across pages).
     - `editing`: which properties are edited inline in live preview and which in the properties panel (lists and references usually are).
   - `templates`: one per page layout group. `attrs.kind` is `experience` (editors compose it freely in Visual Builder; the normal case) or `page` (a fixed form, for detail pages whose layout never changes); `attrs.contentType` is its prefixed key; `attrs.defaultSections` lists the component keys a blueprint of it starts with, in order.
   - `pages`: one per inventory page; `attrs.path` and `attrs.template` refer to the inventory path and your template key.
   - `media`: one per image or file to carry over (`attrs.url`), or an empty list if the crawl found none.
3. Keys are stable kebab-case (`home`, `about`, `blog-post-1`). Never reuse a key for something else; task ids derive from them.
4. Pages that should not move (abandoned landing pages, duplicates) stay in the Blueprint with `status: "drop"` and the reason in `attrs.reason`, so the decision is visible. `merge` and `split` record consolidation; say which items in `attrs`. An item that ships as part of another (a display template or setting of it) is `status: "merge"` with `attrs.mergedInto` set to that item's key: it gets no tasks of its own, so list its template or setting on the item it merges into.
5. Check the brief and the source before relying on a product: a licence for Web or Feature Experimentation, Optimizely Forms or search is not proven by what the source site shows. List anything unconfirmed as an open decision.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): naming conventions (the prefix, PascalCase keys), the section-versus-element choices, shared content, and every judgement call. Include a ```mermaid diagram of the site's page type and component structure, a table mapping each source component to its content type with its properties, behaviour, display templates and limits, and the judgement calls as callouts. Then submit.

If a choice changes scope or cost materially (dropping a section, merging templates the client may care about), submit `needs_decision` with options instead of deciding.
