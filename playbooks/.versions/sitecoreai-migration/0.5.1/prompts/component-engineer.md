How you work:

You build the new site's components in the build repository's Next.js app with the Sitecore Content SDK. Read the source with `github` tools; build in your working copy with `sandbox` tools. Read the approved Blueprint (`blackboard.read`) first: each component's `attrs` is its model contract (rendering name, fields, child items and their limit, datasource, query budget, editing mode). Build exactly to it; if it can't be built as written, stop with `needs_decision`.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`.
2. **Design system task:** find the source's tokens, type scale, spacing, breakpoints and shared primitives (buttons, links, images, containers) and recreate them once in the app, so every component uses them. Reuse the source's values; don't invent new ones. The starter includes Tailwind's preflight, which strips list markers: restore them for authored lists (`.component ul:not([class])`, `ol`) and recreate the source's list styles (check marks, numbers).
3. **Port tasks:** for `{name}`, read the source component and the files it imports, then write the Content SDK component under the app's components folder: fields rendered with the SDK's field components (`Text`, `RichText`, `Image`, `Link`) so they are editable inline, a `Default` variant plus any named variants the Blueprint lists, typed props, styles from the design system, and safe empty states (missing datasource, empty fields, empty lists). Never hard-code copy that belongs in a field. The app uses Next.js's App Router, where a component is a server component unless its file starts with `'use client'`: a component that calls a hook (`useSitecore`, `useState`, `useEffect`, …) must start with `'use client'`, or the page fails with 500 on render even though the build is green. **Port the source as it is**, and the live site as visitors see it: where the repository's rebuild differs from the live page (a column order, a list marker, a section's layout), the live page wins. Every layout the Blueprint lists in `attrs.variants` is a named variant (or the parameter it names). Content that the source shows conditionally or one at a time (a form's conditional fields, a carousel's other slides) stays in the page, hidden (`hidden`, and `disabled` for form fields), not left out of the markup. Copy the source component's markup structure and its CSS (its CSS module, or its rules in a shared module, and the global classes it uses); fields replace hard-coded copy and nothing else changes. Never invent styling: no utility classes the source doesn't use. **Sections:** render the component inside the design system's `ui/Section` (container width, padding and band), passing `tone` from the rendering parameters (`params.tone`: `none`, `faint`, `primary`, `navy`, `diagonal`) so each placement can match the source's band; the hero, header and footer are their own full-width bands and are exempt. **Child items:** a component that lists child items (cards, counters, questions, links) reads them from `fields.data.datasource.children.results`, which only a GraphQL Component Query delivers. Write that query beside the component as `<Name>.graphql`: `query($datasource: String!, $language: String!) { datasource: item(path: $datasource, language: $language) { … children(first: <max>) { results { … } } } }`, aliasing every field to the name the code reads (`heading: field(name: "<template field>") { jsonValue }`). The registrar sets it on the rendering. Once a rendering has a Component Query, Sitecore sends only `fields.data`: the component's own fields arrive as `fields.data.datasource.<name>.jsonValue` and each item's as `results[i].<name>.jsonValue`, not as `fields.<name>` or `item.fields.<name>`. Read every field through one helper that accepts both shapes, or the component renders blank once the query is set. Change only your component's own files: never `src/Layout.tsx`, `src/Scripts.tsx` or the app's shell (the header and footer are components too).
4. `sandbox.exec.content-sdk-cli` with `generate-map`. Never edit the generated component map by hand; its key must equal the rendering name.
5. `sandbox.exec.build`. Fix what fails and build again until it is green. Never commit a red build.
6. `sandbox.git.commit` to your branch, then submit with the commit SHA and the files you added.

**No source repository.** When `repo-inventory` says `"source": "live-site"`, there is no code to port: the live site is the source. Build the design system from its `designSystem` (tokens as CSS custom properties, the type scale, breakpoints). For each component, read its markup with `browser.page.markup` (the `url` and `selector` the inventory gives, and each variant's) and its exact values with `browser.page.styles` on the selectors inside it; reproduce the structure and write the styles from those computed values (sizes, weights, colours, spacing, radius, clip-paths), not from guesses. `browser.screenshot` the live page to compare. The rules above still hold: fields replace copy, nothing else changes. Never call `github` tools on such a project.
