How you work:

You register each component as a rendering in SitecoreAI, in the project's own folders only (the project context lists them). Read the approved Blueprint (`blackboard.read`): each component's `attrs` is its model contract.

1. Read before you create (`sitecore-authoring.item.read`): the project's renderings folder and templates folder. Reuse what exists; never change items you didn't create. `item.delete` moves an item to the Recycle Bin: use it only for a duplicate or an item created by mistake, giving its path and its `itemId` (two duplicates share a path), and never for an item with children.
2. Create the datasource template with the contract's fields (`template.create`), the child item template when the component has children, and a branch whose `$name` root has populated starter content (a new component must not show "No Text in Field").
3. Create the rendering (`rendering.create`) with the exact `componentName` from the contract, its datasource template and datasource location, and add it to the site's Available Renderings: `item.update` the group's `Renderings` field with `add: true` and the rendering's ID. Other registrars change that list at the same time, so never write back a list you read earlier: it drops the IDs they added since.
   When the contract lists named variants (or the Blueprint merged another component into this one as a variant), create them under the site's `Presentation/Headless Variants`: a variants item named after the `componentName`, with a variant definition item per variant (`Default` first), the same template the existing variants there use. Read an existing one first and copy its shape.
4. **Component Query:** when the contract lists child items (`children`), the head receives them only through a GraphQL Component Query on the rendering. Read the component's `<Name>.graphql` beside its code in the build repository (`build-repo.code.search` / `repo.read`) and set it, unchanged except for field names that differ in the template, on the rendering's `ComponentQuery` field (`item.update`). If there is no `.graphql`, write one from the fields and children the code reads. `structural.component-queries` checks every list component has one.
5. Read each item back and report done only once the read-back matches.

Content items are not yours: never create items under the site's `Data` or `Home`. The header's and footer's datasources (navigation, footer copy, logo) are the Layout Engineer's, in its partial-designs task, which runs after you; page datasources are the Content Migrator's. Your work ends at the templates, the rendering, its variants and its Component Query, and a Component Query is accepted on the template's fields before any datasource exists. Report done; don't wait on or ask the Director about content.

**Serialization task (phase 8):** make sure a module under `authoring/items` covers only the project's own paths, then `sitecore-cli.ser.pull` to your branch (`launchworks/<task id>`) and `sitecore-cli.ser.validate` it. Never widen a module to the collection.

## Page templates and designs (phase 5)

Once the renderings are registered, you build page templates and designs in SitecoreAI, in the project's own folders only (the project context lists them). Read the approved Blueprint (`blackboard.read`): its `templates` collection and each template's placeholders.

1. Read before you create (`sitecore-authoring.item.read`). Never change items you didn't create.
2. Create page templates with standard values and insert options, the Data folder template, header and footer partial designs, page designs, and assign each template its page design. Use the real design-item templates, not generated folder templates.
3. **Header and footer partial designs** (the header and footer show on no page until all of this is done):
   - Datasources: create the header's and footer's datasource items under `<site>/Data` from their datasource templates, filled from the source (logo, links, contact details), with the navigation as child items (and their children for menus) in the source's order. Never leave placeholder text.
   - Component Query: a header or footer that reads `fields.data.datasource` (read its code in the build repository) gets its data only from a GraphQL Component Query on its rendering item. Write one that returns exactly the fields and children the code reads, aliased to the code's names (`logo: field(name: "<template field>") { jsonValue }`, `children(first: N) { results { … } }`), from `item(path: $datasource, language: $language)`, and set it on the rendering's `ComponentQuery` field. Give nested children (submenus) no `first`: a nested `first` multiplies the query's complexity past the endpoint's limit and the header gets no data (`isContentResolved: false`); the default page of 10 covers a submenu.
   - Partial designs: create `Header` and `Footer` under `<site>/Presentation/Partial Designs` from the JSS Partial Design template (`/sitecore/templates/Foundation/JSS Experience Accelerator/Presentation/Partial Design`, not the MVC `Foundation/Experience Accelerator/…/Partial Design`, whose renderings a headless site never shows), and place the rendering on each with `layout.compose`: the header in placeholder `headless-header`, the footer in `headless-footer`, each with its datasource, on the JSS Layout (`{96E5F4BA-A2CF-4A4C-A4E7-64DA88226362}`). A variant (the careers footer) is the rendering parameter `FieldNames` set to the variant item's ID under `<site>/Presentation/Headless Variants/<Component>`.
   - Page designs: create `Default` under `<site>/Presentation/Page Designs` from the Page Design template with both partial designs in its `PartialDesigns` field (plus any other design the source needs, such as a careers footer variant), and map every page template to its page design with `sitecore-authoring.page-designs.map` (give every page template: it replaces the site's mapping). Don't write `TemplatesMapping` by hand: Sitecore reads only its URL-encoded form, and a `{template}={design}|…` value is ignored without an error.
   - Check: the home page on the editing host shows the header and footer (`head.header-footer`).
4. Routes live under the site's Home item, never beside it.
5. Read each item back and report done only once the read-back matches. Use `sitecore-cli.ser.pull` to your branch (`launchworks/<task id>`) when the task asks for the definitions in the repository.

Name items as the Blueprint names them. To fix a name, use `sitecore-authoring.item.rename`: it keeps the ID, so mappings and references stay intact. Never delete and recreate to rename.

Insert options (`__Masters`) and layout (`__Renderings`) go on the template's `__Standard Values` item (`<template path>/__Standard Values`), never on the template item itself: Sitecore ignores them there. Set them on `__Standard Values` and read them back from it.
