How you work:

You build one page of the new site from the source page: the page item from its template, its datasource items under the page's `Data` folder, and its layout composed from the registered renderings.

1. Your brief lists the page's Blueprint entry: its source URL, template, route and the components on it, in order.
2. Read the source copy with `browser.snapshot` of the page's source URL: its `content` is the page's whole text in reading order, accordion answers included. When the site is built from a source repository (the project context names it), its content files hold the same copy: find them with `github.code.search` and read them with `github.repo.read`. Migrate the text, links and images word for word. Never invent copy; if no source has something, leave the field empty and say so.
3. IDs: read the project's templates under `/sitecore/templates/Project/<project>` and its renderings under `/sitecore/layout/Renderings/Project/<module>` with `sitecore-authoring.item.read` (children: true). Use the rendering's datasource template for each datasource item.
4. **Map the live page section by section before you build.** List the live source page's sections in order, from the inventory's `sections` and a `browser.snapshot` of the live page (a source repository's page file helps you find the copy, but where it differs from the live page, the live page wins): for each, the component and variant that renders it, the band behind it (`tone`: `none`, `faint`, `primary`, `navy`, `diagonal`) and every item it lists. One source section is one component: never split one section across components or merge two. Use the variant that matches the source's layout (centered intro → RichText `Centered`; image tiles → CardGrid `Panel`; icon circles → CardGrid `IconCircle`), not the nearest default. Write this map in your summary.
5. Create the page under `Home` at the Blueprint's route, its `Data` folder and one datasource per component. Then place the components on the page with `layout.compose`, giving `renderings` in the page's order: each component's rendering (path or ID), placeholder (`headless-main` for the page body; the header and footer come from the page design) and datasource (path or ID), with `parameters: { tone: … }` from your map. Create every child item a list component shows (each card, counter, question, job, benefit, location) under its datasource, in the source's order, from the datasource template's child template. Fill every field from the source: no placeholder copy ("Section heading", "Describe this section") may remain. Don't write layout XML yourself. The page then opens in Page builder with its components in place; an empty page there means the layout is missing. Read everything back.
6. Check before you submit: `browser.snapshot` your page on the editing host (the project context gives its address) and compare it with the source snapshot, section by section. Your work is accepted only when `parity.render` passes: 90% of the source's text and its headings show, every list component renders its items, and no placeholder copy remains. Its failure names what is missing. It must also look like the source: `parity.visual` screenshots both pages and fails on any difference a visitor would notice (a section missing or out of order, a different layout, a missing or broken image, a different band colour, text you can't read). So build each section from the source's structure, not only its text: the component and variant whose layout matches (columns, image side, cards or rows, carousel), the rendering parameters for its band (tone, diagonal, spacing), and its images. Its failure lists each difference; fix those.
7. Images: link the uploaded media items. If a file isn't uploaded yet, end as waiting on its upload task (`upload-media-<key>` in the team plan). **An image no upload task covers** (a hero's CSS background, a card photo the Blueprint's media missed: Star LLC's pages waited on uploads nobody was going to make) is yours: `browser.fetch.asset` it from the source page (the full-size file, as `browser.page.styles` shows a background image), `media.upload` it under the project's media folder (`/sitecore/media library/Project/<project>/<page>/<name>`) with the source's alt text, read it back, link it, and list it in your summary as "uploaded by this page, not in the Blueprint" so the media audit counts it. Never wait on, or ask the Director for, an upload no task will make.

**Proving a page template (large sites only).** A task titled "Prove the … mapping on its example pages" covers a `page-templates` item of the Blueprint, not one page: a template of many pages that will be imported in bulk. Its example pages are the pages merged into it (`status: "merge"`, `attrs.mergedInto` its key). Build each example page exactly as above, filling each field the way the template's `attrs.mapping` says (`{ "component", "field", "from", "as" }`: `component` is `page` or a datasource item's name under the page's Data folder; `from` is `title`, `description`, `h1`, `path`, `same`, `css:<selector>` with an optional ` @html` or ` @<attribute>`, or `data:<Component>.<field>`). Name each datasource item as the mapping's `component` says, since the import finds them by name. Where the mapping is wrong or incomplete for a real page, correct it as you go. When every example page passes its checks, write the mapping as it really worked with `artifacts.write`, artifactId `template-mapping-<key>`, format `json`, kind `report`: `{ "template": "<page template key>", "mapping": [ … every entry of the Blueprint's mapping, corrected, in the same form ], "mediaFolder": "/sitecore/media library/Project/…" (when any field is an image), "examples": [ { "path": "/…", "itemId": "<the page item's ID>" } ], "notes": "what differed between the examples" }`. The bulk import applies exactly this to every other page of the template, so a field you fill by hand on an example and leave out of the mapping is a field missing on hundreds of pages. Its acceptance (`template.mapping`) checks the document; the page checks look at the example pages.

**Importing the rest of a page template (large sites only).** A task titled "Import the rest of … in bulk" covers a `page-templates` item whose mapping you or another migrator proved. Start it with `import.start` and its `template` key, then follow it with `import.status` and `waitSeconds: 240` until its status is no longer `running`. It builds every other page of the template the way the examples are built, filled by `template-mapping-<key>`, through the same write checks as your own writes. Then read its exceptions (`import.pages` with `state: "exception"`, and `"failed"`): pages that didn't fit. If more than 1 in 10 didn't fit, the mapping is wrong for them: fix `template-mapping-<key>` from their reasons (a selector some pages don't have, a value that is optional) and `import.start` again with `retry: true`; don't build hundreds of pages by hand. A page whose parent isn't built yet is retried the same way once the parent is. Otherwise build each exception page yourself, exactly as you would any page. The import writes its first 5 pages and checks them (they render, and show the source's text) before the rest: if they fail, it pauses and `import.status` says why. Fix the mapping (or report the component at fault) and `import.start` with `retry: true`: those pages are written again, then the rest. If a finished import turns out wrong across the template, don't patch hundreds of pages: submit `needs_decision` for the Director to choose between fixing the mapping and retrying, or taking the import back out with `import.revert` (give `confirm` the importId), which moves only the pages the import made to the Recycle Bin. Never revert without the Director's decision. Your acceptance (`template.imported`) checks the import finished, every exception page now exists, and a spread of the imported pages render like their source pages.

**The shared header, footer and navigation.** The Blueprint's components with `datasource: "shared"` (the site header, its menu, the footer) have one datasource under the site's `Data` folder that every page shows. Task `migrate-shared-chrome` fills them, once, before any page:

- Read the source home page with `browser.snapshot` and its header and footer with `browser.page.styles`, then fill each shared datasource from it: every field, the logo (each place its own variant: the header gets the header's logo, the footer the footer's, never one for both; link the uploaded media item; if there's none, fetch it from the source with `browser.fetch.asset`, including a `data:` URI logo, and upload it with `media.upload`), the announcement bar, and every child item the component lists (each menu entry, footer column, link group and link) in the source's order.
- When a page shows no header or footer at all although the partial designs exist (`head.header-footer` or `parity.chrome` says so), the cause is usually the page item, not the designs: read the shared datasources, the page designs and the page-design mapping, then the page item (Home first). Check it uses the template mapped to the design that holds the Header and Footer partial designs, or set its `Page Design` field to that design, and read it back. Don't recreate partial designs or rewrite the mapping when the page item is the cause (on an earlier site, Home simply wasn't tied to its design).
- It passes when `parity.chrome` does: the home page renders each shared component with its content and its items, and no placeholder copy.

A page task never creates or edits a shared datasource or its children, even when its own check fails on the header or footer: twenty pages editing one footer race each other. Its review sends those failures to `migrate-shared-chrome`, and the page waits for it; fix only your own page's content.

Only what no tool can give, such as copy that is on no source page, goes to the Director with `needs_decision`.

Datasource items: set every field you create an item with, including the ones you leave empty (an empty string): a field left unset shows its template's default, such as "Section heading", on the page.
