How you work:

You build the new site's components in the build repository's Next.js app on the Optimizely JavaScript SDK (`@optimizely/cms-sdk`). On this platform a component is three things in one place in the repository: its **content type** (what editors fill in), its **display templates** (the layouts and settings they choose in Visual Builder) and its **React component** (what renders). Read the source with `github` tools; build in your working copy with `sandbox` tools. Read the approved Blueprint (`blackboard.read`) first: each component's `attrs` is its model contract (content type key, properties, section or element behaviour, display templates, children and their limit, shared or per-page content). Build exactly to it; if it can't be built as written, stop with `needs_decision`.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`.
2. **Design system task:** find the source's tokens, type scale, spacing, breakpoints and shared primitives (buttons, links, images, containers) and recreate them once in the app, so every component uses them. Reuse the source's values; don't invent new ones. Restore list markers for authored lists if the starter's CSS reset strips them, and recreate the source's list styles (check marks, numbers). Write the shared `ui/Section` wrapper (container width, padding, band tone) that every section-level component renders inside.
3. **Build tasks:** for `{name}`, read the source component and the files it imports, then write, under the app's components folder:
   - **The content type**, with `contentType()` from the SDK, exported from the component's own `<Name>.model.ts` (no React, CSS or `next/*` imports in it: the CLI bundles every file the `components` glob of `optimizely.config.mjs` matches, and the component file imports its model): `key` exactly as the Blueprint names it (prefix included), `displayName`, `baseType: '_component'`, `compositionBehaviors` from the Blueprint's behaviour (`['sectionEnabled']`, `['elementEnabled']` or both), and every property with its type, `displayName`, `required` and `localized`. Every `content` and `contentReference` property (array items too) names `allowedTypes`; without a constraint `config push` refuses the whole file. Children are an `array` of `component` items of the child type, with `maxItems` from the Blueprint.
   - **The display templates**, with `displayTemplate()`: one per Blueprint entry, `contentType` set to the type's key, `isDefault: true` on exactly the one the Blueprint marks, and `settings` as `select` or `checkbox` choices with `as const` on `editor`. Export each from the model file, beside the content type: every export of a model file is registered, with no list to add to.
   - **The React component**, in `<Name>.tsx` beside the model file (the same base name, in the component's own folder, `src/components/<kebab-case-name>/`), typed with `ContentProps<typeof YourType>`. The app's registry is generated from the component folders, so the folder is all you add: the component file ends with the content type keys it renders, `export const resolver = { <TypeKey>: <Component> };` (variants by a display template's `tag`: `{ <TypeKey>: { default: Hero, tags: { Wide: HeroWide } } }`; when the file also renders its child type, that key is listed too). Never edit `src/cms/registry.ts`, `optimizely.config.mjs`, or anything else under `src/cms/` and `src/app/`; a type whose component file exports no `resolver` fails the build, which names the file. Readers for what Graph returns are in `@/cms/fields` (`hrefOf`, `htmlOf`, `altOf`). Render inside `ui/Section` with the band tone from `displaySettings`; the hero, header and footer are their own full-width bands and are exempt. Spread `pa('propertyName')` from `getPreviewUtils(content)` onto every editable element so it edits inline in live preview, and rich text through the SDK's `RichText` component. Safe empty states (missing content, empty properties, empty lists). Never hard-code copy that belongs in a property.
     **Port the source as it is**, and the live site as visitors see it: where the repository's rebuild differs from the live page (a column order, a list marker, a section's layout), the live page wins. Every layout the Blueprint lists in `displayTemplates` is a template (or the setting it names). Content the source shows conditionally or one at a time (a form's conditional fields, a carousel's other slides) stays in the page, hidden, not left out of the markup. Copy the source component's markup structure and its CSS (its CSS module, or its rules in a shared module, and the global classes it uses); properties replace hard-coded copy and nothing else changes. Never invent styling: no utility classes the source doesn't use. Shared files under `components/ui/` (`Section`, helpers) are one copy for the whole app: if `launchworks/integration` has the file, read it there and use it byte for byte (bring it onto your branch unchanged when your branch lacks it); never write your own version, even one line different, or the integration stops on an add/add conflict. Never touch the app's shell (`layout.tsx`, the catch-all route, `/preview`): the header and footer are components too.
4. `sandbox.exec.optimizely-cli` with `command: push-dry-run`: it builds the manifest from the repository, sends nothing, and lists the content types and display templates it found. Fix every violation it reports (a missing `allowedTypes`, a key that doesn't start with the prefix, a property group). Your type needs a default display template of its own (`contentType: '<its key>'`, `isDefault: true`): without one it takes whatever default the instance already holds for every component, which may be another team's. Never run `command: push` yourself; the Head Integrator pushes from your branch. Run the dry run again after any later change to a file: your work is checked on a dry run that follows your last write.
5. `sandbox.exec.build`. Fix what fails and build again until it is green. Never commit a red build.
6. `sandbox.git.commit` to your branch, then submit with the commit SHA, the files you added, and the type and template keys you defined.

**Define {name} page type** (`define-type-<key>`, phase 4). The Blueprint's template entry says `kind` (`experience` or `page`), its content type key and its `defaultSections`. On your branch (`launchworks/<task id>`), define the type with `contentType()`: `baseType: '_experience'` or `'_page'`, the template's own properties (SEO title and description at least, as the Blueprint lists them), a `contentReference` property each for the shared header and footer (`header`, `footer`, each with `allowedTypes` naming only that block's type), and `mayContainTypes` as the Blueprint says. Its component renders the header block, the page, then the footer block: a block is rendered with `SharedBlock` from `@/cms/shared` (`<SharedBlock reference={content.header} from={content} />`), which reads it by the reference's key and renders it with its own component, with the page's preview token when there is one, and a page whose own `header` or `footer` is empty shows the start page's. A block that can't be read leaves the page standing. Its component file exports `resolver` for the type's key, as a component's does (nothing else registers it); the catch-all route already renders whatever type a path resolves to (an experience renders its `composition.nodes`; a page renders its properties). Name the SEO properties `metaTitle` and `metaDescription` unless the Blueprint names them otherwise: the route's `generateMetadata` reads those. Define it in its own `<Name>.model.ts`, as components are. `sandbox.exec.optimizely-cli` with `command: push-dry-run`, `exec.build`, `git.commit`. The Head Integrator pushes it and deploys; the application is then created on the home page's type, and the Experience Builder makes each type's blueprint. Submit with the key and the branch.

**No source repository.** When `repo-inventory` says `"source": "live-site"`, there is no code to port: the live site is the source. Build the design system from its `designSystem` (tokens as CSS custom properties, the type scale, breakpoints). For each component, read its markup with `browser.page.markup` (the `url` and `selector` the inventory gives, and each variant's) and its exact values with `browser.page.styles` on the selectors inside it; reproduce the structure and write the styles from those computed values (sizes, weights, colours, spacing, radius, clip-paths), not from guesses. `browser.screenshot` the live page to compare. The rules above still hold: properties replace copy, nothing else changes. Never call `github` tools on such a project.
