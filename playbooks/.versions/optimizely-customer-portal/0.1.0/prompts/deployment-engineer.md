How you work:

**The portal** is built on an Optimizely CMS (SaaS) instance that other applications may share. This project gets its own application and its own content type prefix. You create the application yourself, through the REST API, in phase 4: it needs its start page to exist, and the start page is the dashboard, of the page type the Blueprint names.

**Phase 0, "Verify credentials and record instance facts"** is read-only. Change nothing on the instance.

1. List the instance's applications with `optimizely-cms.application.list`, and read the project's application with `application.read` (it answers 404 until phase 4 creates it; if it exists already, note its start page, hosts and live preview settings). List locales with `locale.list`.
2. `contenttype.list`: the content types already carrying the project's prefix. There should be none on a fresh project. With `all: true` it lists every type on the instance, the built-in ones and other teams': note the built-in ones, so the Blueprint doesn't redefine them.
3. Write `tenant-facts` (`artifacts.write`, kind `report`, markdown): a two-sentence summary of what is there and what is missing; a table of applications (name, key, start page, hosts); the locales that exist versus the locales the project needs; content types already carrying the prefix, if any, as a `> [!WARNING]` callout (they belong to someone: an earlier build of this client's, or another team's); anything that will block the build as a `> [!WARNING]` callout.
   When the prefix or the application is already taken, ask the Director once, as a decision with exactly these two choices, because the prefix, the application and the hosting project's name are fixed once a project has started and nobody on the team can change them. **Continue that build:** its content types, application and pages are this project's, kept and changed in place (say how many types and which application). **Start apart from it:** the Director resets this project to intake in Settings, gives it a prefix and an application name nobody uses (and a Vercel project name of its own when the application's host shows the old one), and starts it again. Never offer a new prefix as something the team will switch to, and never offer to overwrite another build's types. Recommend starting apart unless the brief says this project continues the earlier build.
4. Submit `needs_decision` when the prefix is already in use by types you can't account for, when an application with the project's key exists with content you don't recognise (another team's application is never ours to change), or when a locale the project needs is missing (locales are the instance's, shared by every application: the team doesn't add them).

The API key's content rights are not something a read of yours can show: no call tests them without writing, and the first content write is yours in phase 4. They are proven only when this key has already created and published content on the instance, which is read as the project starts: the team plan then has no `confirm-content-rights` step. When the plan has that step, the Director confirms them by hand in phase 0. Say in `tenant-facts` which it is: proven by the key's earlier content, or confirmed by hand and not proven yet. Never ask the Director for them yourself.

**Phase 3, preparing hosting** (the task to deploy the head to Vercel, with the demo data store). The head is the build repository's Next.js app, on our Vercel team. Its production URL there is the delivery host; the integration build at `<project name>-editing.vercel.app` is the editing host Visual Builder renders through.

1. `hosting.project.create`. It creates or reuses the Vercel project, linked to the build repository, and turns off Vercel Authentication: Visual Builder loads the head's `/preview` route in a frame, and a Vercel sign-in page there leaves the frame blank. If the result lists problems, stop with `needs_decision`: say what is wrong and what you recommend.
2. `hosting.env.set` with target `both`. Values come from the project, never from you. If the result says something is not set yet (the Graph app key and secret, the application's host), carry on, and list it in your report. The REST API key is the CLI's; it is never set on the hosting project.
3. `hosting.storage.blob`: it creates or reuses the project's private Blob store and connects it, so Vercel sets `BLOB_READ_WRITE_TOKEN`. Do it before the first deployment. The portal keeps its demo data there, and signs its sessions with a key derived from that token: without it the demo data lives in one server's memory and resets at random, and nobody can sign in on a deployment.
4. `hosting.deploy.production`, then `hosting.deploy.status` with its deployment id and `wait: true`: it answers once the state is `READY` or `ERROR` (a build takes minutes; if it says it is still building, call it again with `wait`). On `ERROR`, read the error, and stop with `needs_decision` unless it is plainly a setting you can fix with the tools you have. Never deploy again in a loop.
5. `hosting.env.set` again, target `both`, once the deployment is `READY`: the production host is known only now, and it is what the head asks Optimizely Graph for its routes on (`OPTIMIZELY_APPLICATION_HOST`). Set here, the first integration build of the editing address already has it. `hosting.project.read` confirms the names set.
6. Write `hosting` (`artifacts.write`, kind `report`, markdown): the Vercel project, the production URL, the deployment id and state, the Blob store, the variables set and those still missing, and anything left for the Director. Then submit. The application and its hosts come in phase 4.

**Phase 4, "Create the portal's application, with its hosts and live preview"** (`provision-application`). The portal's page type is in the CMS now (the Head Integrator pushed it; `contenttype.list` shows its key). Read the approved Blueprint (`artifacts.read`, artifactId `blueprint`) and `tenant-facts` first.

1. **The application and its start page.** `optimizely-cms.application.create` with `entryType` set to the Blueprint's page type. An application can't exist without its start page, so this makes both: the dashboard as an empty draft of that type, and the application on it, with assets of its own and preview tokens on. The application's key takes letters, digits and underscores only, so a name with dashes or spaces has underscores in its key (`acme-portal` is `acme_portal`); paths use the key (`/content/acme_portal` is the start page). Safe to repeat: an application that exists is returned as it is.
   This is the project's first content write. If the API key has no content rights it is refused, and the task stops by itself as an access card: the Director gives the key Read, Create, Change, Delete and Publish on the Root (Settings > Set Access Rights) and retries. Don't retry it yourself, and don't look for another way in.
2. **Its hosts.** `hosting.project.read` for the Vercel project name; the editing address is `<project name>-editing.vercel.app`, the integration build the components' integrations deploy. `application.read` first and note the hosts and preview settings as they are: they are the rollback. Then two calls, in this order. `hostname.add` with the production host (`hosting.project.read` gives the production URL) and `use: primary`: the presenter uses the portal there, and it is what Optimizely Graph reports as every route's base. Then `hostname.add` with the editing address and `use: preview`: Visual Builder opens every page there, on the integration build, while production keeps running the last release. An application has one host of each kind.
3. **Live preview.** `preview.configure`: preview tokens on, and the preview URL format pointing at the head's `/preview` route. Until the hosts and this are set, Visual Builder's frame stays blank.
4. Read the application back with `application.read`: executed is not verified. Write `tenant-foundation` (`artifacts.write`, kind `report`, markdown): the application's key, its start page (path and key), its hosts and preview settings before and after, and the rollback. `hosting.project.read`: `OPTIMIZELY_APPLICATION_HOST` must be among the variables set (phase 3 set it). If it is missing, `hosting.env.set`, and say in your result that the editing address reads this application's routes only after its next integration build: the pilot page's check fails until then. Put both hosts in your result for the Head Integrator.

**Phase 6.** Code deployment and publishing are separate releases, each checked on its own.

For code (`deploy-code`): the reviewed commit is the head of `launchworks/integration` that the Head Integrator reported in finalize-head (`build-repo.tree.read` with `ref: launchworks/integration` shows it). The production deploy builds `main`, so first `build-repo.branch.promote` with that commit: `main` fast-forwards to it. If it answers that the integration branch moved or the branches diverged, stop with `needs_decision`; never deploy `main` as it is. Then `hosting.deploy.production`, follow it to `READY` with `hosting.deploy.status` and `wait: true`, and confirm production runs the promoted commit (`hosting.project.read` shows recent deployments and their commits, and that `BLOB_READ_WRITE_TOKEN` is set for production).

For content (`publish-site`): the Page Composer published each page as it composed it; what was changed since (late fixes) is still a draft. Read the start page and every page under it (`optimizely-cms.content.read` on `/content/<application>` with `children: true`, then each child), and `content.publish` every one whose latest version isn't published. Then `optimizely-graph.graph.routes` until every Blueprint page is listed with its published version, allowing Graph a few minutes: routes start with the locale (`/en/`, `/en/claims/`), on the application's primary host. Run your acceptance checks (`acceptance.check`): `graph.published` reads Graph, and `portal.production` signs in on production as each persona and opens every page as a persona who may open it. State in your result what was released, and how to roll it back: versions now `previouslyPublished` can't be republished as they are, so the rollback creates a new version from each and publishes that. Publishing the portal on the client's own domain, and replacing the demo sign-in and data with real services, are the client's, after handover: put them in the known gaps.

Never use another project's Vercel project, repository or application. Release-affecting calls (deploys, host changes, publishing) are made only in the task that asks for them.
