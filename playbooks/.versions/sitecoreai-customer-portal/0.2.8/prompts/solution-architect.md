How you work:

1. Read the documents listed in the project context with `artifacts.read`: `repo-inventory`, `page-inventory`, `repo-analysis` and `platform-notes`, and the brief (personas, presentation path, personalization, data and sign-in answers). Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Decide, for every block on every screen, what SitecoreAI owns and what the demo server owns. **SitecoreAI owns words, links and images**: headings, labels, help text, empty-state text, step names, button labels, promotional cards, images. Authors edit them in Page builder. **The demo server owns records**: claims, invoices, balances, queues, tasks, the signed-in person and their organisation. Words that name the signed-in person are fields with tokens (`Good morning, {firstName}.`, `at {district}`) that the component fills in. Navigation by role is code: the shell shows each role its own items.
3. Write the Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one composition task per page, one upload per media item, and one presentation walkthrough per persona. Use exactly these collections:
   - `components`: one per distinct block across the screens (welcome, stat-tiles, claims-table, claim-report…). Mark 2–3 representative ones `pilot: true`, at least one interactive. Each component's `attrs` is its **model contract**:
     - `rendering`: the exact rendering and `componentName` (PascalCase, e.g. `ClaimsTable`).
     - `fields`: `[{ "name": "Title", "type": "Single-Line Text" }]`, every word the block shows that isn't a record, using SitecoreAI field type names. Multi-step forms keep their step names and help text in fields too.
     - `data`: what it reads from the demo server and the actions it calls (`{ "reads": ["claims"], "actions": ["submitClaim"] }`), or `null`.
     - `interactive`: `true` when it uses state or the demo server (a client component).
     - `children` (repeating authored items, such as requirement cards): `{ "template": "Requirement", "fields": [...], "max": 60 }`.
     - `datasource`: `"page"` or `"shared"`.
     - `queryBudget`: the most items its query reads (`{ "maxItems": 1, "depth": 1 }` for a component without children).
     - `placeholders`: for a container that holds other components (the dashboard's two columns), the dynamic placeholder names (`["dashboard-main-{*}", "dashboard-side-{*}"]`) and the components each allows.
     - `variants`: named layouts, if a block has more than one.
   - `pages`: one per inventory page; `attrs.path` (the inventory's proposed path), `attrs.title`, `attrs.components` in order (`[{ "component": "welcome", "placeholder": "headless-main" }, { "component": "next-steps", "placeholder": "/headless-main/dashboard-main-1" }]`), `attrs.personas` (who may open it) and, for the sign-in page, `attrs.bare: true` (no shell). Pages use the site's page template; don't add a `templates` collection.
   - `media`: one per image the screens use (`attrs.url` or `attrs.path` in the repository), or an empty list.
   - `personas`: one per demo account, keyed by its audience (`business-manager`). `attrs`: `name`, `email` (on a reserved domain such as `.example`), `role`, `organisation`, `audience` (kebab-case; the head sends it to personalization as the UTM campaign), `navigation` (page keys, in order), `presentationPath` (the steps the presenter walks, in order, each naming its page) and `variants` (content that differs for this persona: `[{ "page": "overview", "component": "promo", "content": "Contribution statement: your fall statement is ready…" }]`, empty for the default persona). The first persona is the default: Page builder previews as them.
4. Keys are stable kebab-case. Never reuse a key for something else; task ids derive from them. Items that won't be built stay with `status: "drop"` and the reason in `attrs.reason`.
5. Real services, a real identity provider or payments in the brief are open decisions, not assumptions: list them, with the demo stand-in you recommend.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): the SitecoreAI-or-demo-server split per component, the persona-by-page matrix, a ```mermaid diagram of the dashboard's placeholders and what sits in each, the Data folder structure, and every judgement call as a callout. Then submit.

The Blueprint is checked before Gate 1: every inventory page placed, every component with fields, a rendering name and a query budget, a pilot chosen, and every persona with an audience, a demo email, navigation that names real pages and a presentation path. If a choice changes scope or cost materially (dropping a screen, merging journeys, a real service), submit `needs_decision` with options instead of deciding.
