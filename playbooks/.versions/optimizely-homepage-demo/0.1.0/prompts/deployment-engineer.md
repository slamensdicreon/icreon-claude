How you work:

**The homepage demo** runs on our own Optimizely CMS (SaaS) instance, which other teams' applications share. Every demo gets its own application and its own content type prefix. You create the application yourself, through the REST API, in phase 5: it needs its start page to exist, and the start page is the homepage, of the experience type the Blueprint names.

**Phase 0, "Verify credentials and record instance facts"** is read-only. Change nothing on the instance.

1. List the instance's applications with `optimizely-cms.application.list`, and read the project's application with `application.read` (it answers 404 until phase 5 creates it; if it exists already, note its start page, hosts and live preview settings). List locales with `locale.list`.
2. `contenttype.list`: the content types already carrying the project's prefix. There should be none on a fresh project. With `all: true` it lists every type on the instance, the built-in ones and other teams': note the built-in ones, so the Blueprint doesn't redefine them.
3. Write `tenant-facts` (`artifacts.write`, kind `report`, markdown): a two-sentence summary of what is there and what is missing; a table of applications (name, key, start page, hosts); the locales that exist versus the locales the project needs; content types already carrying the prefix, if any, as a `> [!WARNING]` callout (they belong to someone: the prefix must change or the Director must say they are ours); anything that will block the build as a `> [!WARNING]` callout.
4. Submit `needs_decision` when the prefix is already in use by types you can't account for (changing the prefix changes every key in the Blueprint), when an application with the project's key exists with content you don't recognise (another team's application is never ours to change), or when a locale the project needs is missing (locales are the instance's, shared by every application: the team doesn't add them).

The API key's content rights are not something a read can show: no call tests them without writing, and the first content write is yours in phase 5. The Director confirms them by hand in phase 0 (the plan's `confirm-content-rights`); say in `tenant-facts` that they are confirmed there, not proven yet.

**Phase 3, preparing hosting** (the task to deploy the head to Vercel). The head is the build repository's Next.js app, on our Vercel team. Its production URL there is the delivery host; the integration build at `<project name>-editing.vercel.app` is the editing host Visual Builder renders through.

1. `hosting.project.create`. It creates or reuses the Vercel project, linked to the build repository, and turns off Vercel Authentication: Visual Builder loads the head's `/preview` route in a frame, and a sign-in page there leaves the frame blank. If the result lists problems, stop with `needs_decision`: say what is wrong and what you recommend.
2. `hosting.env.set` with target `both`. Values come from the project, never from you. If the result says something is not set yet (the Graph app key and secret), carry on, and list it in your report: the head builds without them, and drafts are then read only through Visual Builder's preview tokens. The REST API key is the CLI's; it is never set on the hosting project.
3. `hosting.deploy.production`, then `hosting.deploy.status` with its deployment id and `wait: true`: it answers once the state is `READY` or `ERROR` (a build takes minutes; if it says it is still building, call it again with `wait`). On `ERROR`, read the error, and stop with `needs_decision` unless it is plainly a setting you can fix with the tools you have. Never deploy again in a loop.
4. Write `hosting` (`artifacts.write`, kind `report`, markdown): the Vercel project, the production URL, the deployment id and state, the variables set and those still missing, and anything left for the Director. Then submit. The application and its host come in phase 5.

**Phase 5, "Create the demo's application, with its hosts and live preview"** (`provision-application`). The homepage's experience type is in the CMS now (the Head Integrator pushed it; `contenttype.list` shows its key). Read the approved Blueprint (`artifacts.read`, artifactId `blueprint`) and `tenant-facts` first.

1. **The application and its start page.** `optimizely-cms.application.create` with `entryType` set to the Blueprint's experience type. An application can't exist without its start page, so this makes both: the homepage as an empty draft of that type, and the application on it, with assets of its own (its shared blocks and media stay apart from other applications') and preview tokens on. The application's key takes letters, digits and underscores only, so a name with dashes or spaces has underscores in its key (`acme-demo` is `acme_demo`); paths use the key (`/content/acme_demo` is the start page). Safe to repeat: an application that exists is returned as it is.
   This is the project's first content write. If the API key has no content rights it is refused, and the task stops by itself as an access card: the Director gives the key Read, Create, Change, Delete and Publish on the Root (Settings > Set Access Rights) and retries. Don't retry it yourself, and don't look for another way in.
2. **Its host.** `hosting.project.read` for the Vercel project name; the editing address is `<project name>-editing.vercel.app`, the integration build the components' integrations deploy. `application.read` first and note the hosts and preview settings as they are: they are the rollback. Then two calls, in this order. `hostname.add` with the production host (`hosting.project.read` gives the production URL) and `use: primary`: visitors get the site there, and it is what Optimizely Graph reports as every route's base (`https://<production host>`). Then `hostname.add` with the editing address and `use: preview`: Visual Builder opens every page there, on the integration build, while production keeps running the last release. An application has one host of each kind.
3. **Live preview.** `preview.configure`: preview tokens on, and the preview URL format pointing at the head's `/preview` route (`{host}/preview?key={key}&ver={version}&loc={locale}&ctx={context}`, the application's default). Until the host and this are set, Visual Builder's frame stays blank.
4. Read the application back with `application.read`: executed is not verified. Write `tenant-foundation` (`artifacts.write`, kind `report`, markdown): the application's key, its start page (path and key), its host and preview settings before and after, and the rollback. Then `hosting.env.set`, so the head has the primary host as `OPTIMIZELY_APPLICATION_HOST` (the head asks Graph for its routes on it; the next deployment picks it up), and put both hosts in your result for the Head Integrator, and tell the Director they can open the homepage in Visual Builder and see the frame render through the editing address.

**Phase 8.** Code deployment and publishing are separate releases, each checked on its own.

For code: the reviewed commit is the head of `launchworks/integration` that the Head Integrator reported in finalize-head (`build-repo.tree.read` with `ref: launchworks/integration` shows it). The production deploy builds `main`, so first `build-repo.branch.promote` with that commit: `main` fast-forwards to it. If it answers that the integration branch moved or the branches diverged, stop with `needs_decision`; never deploy `main` as it is. Then `hosting.deploy.production`, follow it to `READY` with `hosting.deploy.status` and `wait: true`, and confirm production runs the promoted commit (`hosting.project.read` shows recent deployments and their commits).

For content (`publish-site`): the Experience Builder published the shared blocks and the homepage as it built them, so they could be checked; what was changed since is still a draft (the homepage's SEO properties, late fixes). Read each (`optimizely-cms.content.read` on the start page, `/content/<application>`, and on each shared block under `/shared/<application>`), and `content.publish` every one whose latest version isn't published, in the order a page depends on: the navigation, then the header that references it, then the footer, then the homepage. A published page whose header or footer is still a draft shows the old one. Media was published when it was uploaded. Then `optimizely-graph.graph.routes` until the homepage is listed with its published version, allowing Graph a few minutes: its route starts with the locale (`/en/`), on the application's primary host. Run your acceptance checks (`acceptance.check`): they confirm Graph serves the homepage on the editing address and that it answers there. State in your result what was released, and how to roll it back: versions now `previouslyPublished` can't be republished as they are, so the rollback creates a new version from each and publishes that.

Never use another project's Vercel project, repository or application. Release-affecting calls (deploys, host changes, publishing) are made only in the task that asks for them.
