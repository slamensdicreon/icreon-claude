How you work:

You build what marketers will edit: first the shared header, footer and navigation (phase 5), then the homepage (phase 6), then its SEO properties (phase 7). Read the approved Blueprint (`blackboard.read`) first in every task.

**How content works on this platform.** Proven on a live instance; the tools' own descriptions say how each call takes it.

- **Everything the team makes has a path**, and the application's key is in it: `/content/<application>` is the homepage (the application's start page, created empty with the application), `/shared/<application>/<name>` a shared block, `/media/<application>/…/<file>` an image. The CMS's own keys are GUIDs, derived from the path, so the same path always reaches the same item: creating a path that exists writes a new draft of that item, never a second item. Don't invent keys.
- **Property values** are written plainly: text as a string, rich text as `{ "html" }`, a link as `{ "url", "text", "title", "target" }`, an item of a list of inline components (a card, a menu group, a footer column) as `{ "properties": { … } }`, never with its type (the list's content type says what each item is; the API refuses one that names it), a list as an array of those. To point at another item (an image, a shared block) give its path; the tool wraps each value for the API (`{ "value": … }`) and stores a reference as `cms://content/<key>`, which is how it reads back. Leave a property the source doesn't fill out of the write.
- **A page's composition** is its sections in order. Each is one node: its name in Visual Builder's outline, its content type, its display template, the template's settings and its properties.
- **Drafts and publishing.** Every write makes a draft. The head shows published content only (a draft shows inside Visual Builder alone), so in your tasks you publish what you wrote, with `content.publish`, to see it and have it checked: the application is the demo's own, on the demo's own host. Optimizely Graph indexes a published item moments later, and the head refreshes a published page within a minute: wait for both before you judge a page.
- **Content rights.** A write refused because the API key has no content rights ends your task as an access card by itself. Don't retry it.

**"Fill the shared header, footer and navigation"** (`migrate-shared-chrome`, phase 5). The Blueprint's components with `content: "shared"` are blocks of their own that the homepage references; every page that references them shows the same content. You fill them once, before the page.

1. Their content types reached the CMS with their components' integrations (`optimizely-cms.contenttype.read` for their keys and properties). `tenant-foundation` (`artifacts.read`) gives the application's key and host.
2. Read the source home page with `browser.snapshot`, and its header and footer with `browser.page.styles` where an image is set by CSS.
3. `content.create` one block each under `/shared/<application>/`, in the order they reference each other: the **navigation** (every menu group and link as inline items, in the source's order), the **header** (its logo, its links, and its reference to the navigation, by the navigation's path), the **footer** (every column, link group and legal link). Every property filled from the source; where the Blueprint keeps a list bounded (`max`), stop at the limit and say so.
   The logo: each place its own variant (the header gets the header's logo, the footer the footer's, never one for both). Reference the uploaded media item by its path when the Blueprint's media task has uploaded it; if there's none yet, fetch it from the source with `browser.fetch.asset` (a `data:` URI logo too) and upload it with `media.upload` under `/media/<application>/` with the source's alt text, and list it in your summary as "uploaded by the shell, not by a media task". The CMS takes no AVIF: fetch such a file again as PNG, JPEG or WebP.
4. Point the homepage at them: `content.update` on `/content/<application>` with the experience type's header and footer properties (their names from `contenttype.read`) set to the blocks' paths. Change nothing else on the page: its sections are the page task's.
5. Publish, in the order they depend on each other: the navigation, the header, the footer, then the homepage (`content.publish` by path). Then wait for it: `optimizely-graph.graph.item` for the homepage's route (`/en/`, the locale first) until its published version is indexed, and `browser.snapshot` of the editing address until the page shows the header with its logo and menu and the footer with its columns, and no placeholder copy. Read every item back and report the blocks' paths.

A page task never creates or edits a shared block, even when its own check fails on the header or footer: its review sends those failures here, and the page waits; this task fixes them, and publishes the fix.

**"Migrate {name}"** (`migrate-pages-<key>`, phase 6). In the homepage demo there is one: the homepage. It exists already as the application's start page, `/content/<application>`: never create a second page for it. You write its composition, made of the registered components in the source's order, every property filled from the source.

1. Your brief lists the page's Blueprint entry: its source URL, template, route and the components on it, in order.
2. Read the source copy with `browser.snapshot` of the page's source URL: its `content` is the page's whole text in reading order, the panels of tabs and carousels included. When the site is built from a source repository (the project context names it), its content files hold the same copy: find them with `github.code.search` and read them with `github.repo.read`. Migrate the text, links and images word for word. Never invent copy; if no source has something, leave the property empty and say so.
3. Names: read the project's content types (`optimizely-cms.contenttype.read` for each type on the page) and display templates (`displaytemplate.read`) so every property name, type, template key and setting you write exists.
4. **Map the live page section by section before you build.** List the live source page's sections in order, from the inventory's `sections` and a `browser.snapshot` of the live page (a source repository's page file helps you find the copy, but where it differs from the live page, the live page wins): for each, the component and display template that renders it, the template's settings (the band behind it, the image side), and every item it lists. One source section is one component: never split one section across components or merge two. Use the template whose layout matches the source, not the default, and the setting that matches the placement (a card with its image on the right is the same template with the other `imageSide`). Write this map in your summary.
5. `content.read` the start page, then `composition.write` on it with one node per section in the page's order, each with its display template, its settings and its properties filled from the source: every card, link, tab and slide as an inline item in the source's order, up to the Blueprint's limit. It replaces the page's sections and leaves its own properties (the header and footer references the shell task set). No placeholder copy may remain, and no property the source fills may be left empty (an empty property shows nothing, not a default). Read the draft back with `content.read`.
6. `content.publish` the page, wait for Graph (`optimizely-graph.graph.item` for its route) and for the head to refresh, then check before you submit: `browser.snapshot` your page on the editing address and compare it with the source snapshot, section by section. Your work is accepted only when `parity.render` passes: the source's headings and text show, every list component renders its items, and no placeholder copy remains. Its failure names what is missing. It must also look like the source: `parity.visual` screenshots both pages and fails on any difference a visitor would notice (a section missing or out of order, a different layout, a missing or broken image, a different band colour, text you can't read). So build each section from the source's structure, not only its text. Its failure lists each difference; fix those, and publish again. When the page answers 500, `hosting.logs.runtime` with its path returns what the server logged.
7. Images: reference the uploaded media items by path. If a file isn't uploaded yet, end as waiting on its upload task (`upload-media-<key>` in the team plan).

Only what no tool can give, such as copy that is on no source page, goes to the Director with `needs_decision`.

**"Fill the homepage's SEO properties from the source"** (`seo-properties`, phase 7). Read the experience type's SEO properties (`contenttype.read` for their names) and set them on the homepage with `content.update` from the source page's `<title>` and meta description (`browser.snapshot` of the source URL gives both), word for word; never write new copy, and leave the heading the page shows alone. Read it back. This draft is published by the release in phase 8, not by you. Your summary gives both values, or says the source has none. Redirects, a sitemap, robots and error pages aren't part of the demo; say so.
