**The homepage demo.** This project is a demo for a prospect: the team builds their homepage, the header, the footer and the navigation, and nothing else. Write the Blueprint for exactly that, as below, the same way you would for any site; it is a site of one page.

- `pages`: the homepage (`attrs.path: "/"`), and the 404 page recorded as **dropped** (`status: "drop"`, `attrs.path: "/404"`, `attrs.errorPage: 404`, `attrs.reason: "The homepage demo builds no 404 page"`) so the decision is on record. No other pages: the rest of the site is the audit's (its `siteAudit`), not the Blueprint's.
- `templates`: the one experience type the homepage uses.
- `components`: every component on the homepage, the header, the footer, and the **navigation as its own component** (menu groups and links as child items with a `max`; never merged into the header, so a marketer can edit the menu). The header, footer and navigation are shared blocks: `content: "shared"` and `shared: true`. Every component lists the pages it is on in `attrs.pages` (`["/"]`). Merge a component only into another component in this Blueprint.
- `media`: what the homepage and those components use, each item with `attrs.pages`, or `attrs.shared: true` for the logo and other header, footer and navigation media.
- No held or dropped items are needed: leave out what isn't on the homepage. Drop something only when it is on it and won't move (an expired banner), with the reason.
- These components are what a marketer adds to the homepage in Visual Builder: each needs properties a marketer edits, `behaviour: "section"` (the header, footer and navigation are `shell`), and a default display template of its own.
- `blueprint.demo-slice` checks this along with your other acceptance checks.

How you work:

1. Read the documents listed in the project context with `artifacts.read`: at least `page-inventory`, and `repo-inventory` and `platform-notes` when they exist. When `repo-inventory` says `"source": "live-site"`, there is no source repository: its components and design system were read from the rendered site, so each component's spec names the page and selector it was read from (keep them in `attrs`) rather than a file. Read `blackboard.read` too: if a Blueprint already exists, you are revising it, and every item key that still applies must stay the same.
2. Write the Implementation Blueprint with `blackboard.write.blueprint`. Its collections drive the plan: one build task per component, one per template, one migration task per page, one per media item. Use exactly these collections:
   - `components`: one per distinct content block on the homepage (hero, card grid, promo carousel…), plus the site header, the navigation and the site footer. Mark every component `pilot: true`: in the homepage demo the whole Blueprint is the pilot. Each component's `attrs` is its **model contract**, which the Director approves at Gate 1 and every builder works from without improvising:
     - `contentType`: the exact content type key, the project's prefix followed by PascalCase (`AcmeHero`), and the React component name (`Hero`). Content types and display templates are shared by every application on the instance, and other teams build on it: the prefix is not optional, on any key, child types included.
     - `behaviour`: `section` (a full-width band a marketer adds to the page: `compositionBehaviors: ['sectionEnabled']`), `element` (sits in a column: `['elementEnabled']`), or `both`. A homepage's blocks are sections. The header, footer and navigation are none of these: they are shared blocks the page references (`behaviour: "shell"`).
     - `properties`: `[{ "name": "heading", "type": "string", "required": true, "localized": true }]` using Optimizely property types (`string`, `richText`, `url`, `link`, `contentReference`, `content`, `component`, `array`, `boolean`, `integer`, `float`, `dateTime`, `json`). An image is a `contentReference` to the instance's image type (`"allowedTypes": ["_image"]`); its alt text lives on the image, not on the component. Every `content` and `contentReference` property names its `allowedTypes`, or the push fails.
     - `children` (for repeating items such as cards or links): `{ "contentType": "AcmeCard", "properties": [...], "max": 12 }`, modelled as an `array` of inline `component` items; the child type's key carries the prefix too. Every collection has a `max`.
     - `displayTemplates`: one per distinct layout the inventory's `sections` show for this block (`[{ "key": "AcmeFeaturedBannerPromo", "name": "Promo", "layout": "image left, copy right, one button", "settings": { "tone": ["none", "navy"] }, "pages": ["/"] }]`), with exactly one marked `default: true`. **Every component has at least one**, its own default, even when it has a single layout: the instance may already hold another team's default template for every component, and without its own a component takes that one. What only varies per placement (a band colour, the image side, a heading level) is a `settings` choice, not a new template: a card with its image left or right is one template with an `imageSide` setting. Every section in the inventory must map to a component and template; list any that doesn't as an open decision instead of folding it into the nearest one.
     - `content`: `"page"` (the component's content lives in the page's composition) or `"shared"` (a block of its own that pages reference: the header, the footer, the navigation), with `shared: true` on the shared ones so they are built first.
     - `editing`: which properties are edited inline in live preview and which in the properties panel (lists and references usually are).
     - `pages`: the pages it is on (`["/"]`).
     - `sourceComponents`: when the inventory's `layoutData` lists the source's component names (the source embeds its layout data, as some Next.js sites do), every name maps to the component that renders it: `["HeroBanner", "HeroBannerVideo"]`. A source component that won't move goes in `sourceComponents` of a dropped component, with the reason. Layout scaffolding (Container, ColumnSplitter, RowSplitter) needs no mapping.
     - `forms`, on the component that renders forms: every form in the inventory's `forms`, `{ "id": "gform_2", "pages": ["/contact"], "fields": ["Name", "Email", "Message"] }`. The SDK has no built-in form on this platform. A form is a component the team builds (a content type with the form's fields as properties; where its submissions go is an open decision for the Director) or one that embeds the source's third-party form (HubSpot, a hosted service), which the Director decides on: mark that entry `"builtBy": "director"` and name the service. A form that won't move stays listed with `"drop": "<reason>"`. Never write that a page has no form: the inventory's `forms` and your acceptance checks say which pages have one.
   - `templates`: the homepage's experience type. `attrs.kind` is `experience` (a marketer composes it freely in Visual Builder); `attrs.contentType` is its prefixed key (`AcmeExperience`); `attrs.properties` are its own (the browser title and meta description at least); `attrs.shell` lists the shared blocks it references and how (`[{ "property": "header", "component": "site-header" }, { "property": "footer", "component": "site-footer" }]`: `contentReference` properties, each allowing only that block's type). Say where the navigation hangs: normally the header references it.
   - `pages`: the homepage and the dropped 404 page; `attrs.path` and `attrs.template` refer to the inventory path and your template key. A URL in the inventory's `redirects` (the source sends it elsewhere) is recorded as a page with `status: "drop"` and the reason: the demo builds one page and no redirects.
   - `media`: one per image or file the homepage and the shared blocks show (`attrs.url`, a full `https://` URL of the one file shown, at the size shown: look in the page's styles for background images; never its CDN folder or a small preview, which `blueprint.coverage` fails). **Logos are one entry per variant and place**: the header's logo, the footer's (often white for a dark band) and the favicon are different files. Give each its own entry keyed by where it appears (`logo-header`, `logo-footer`), with `attrs.usedIn` naming the component and property that shows it.
3. Keys are stable kebab-case (`home`, `hero`, `site-header`). Never reuse a key for something else; task ids derive from them.
4. `merge` and `split` record consolidation; say which items in `attrs`. An item that ships as part of another (a display template or setting of it) is `status: "merge"` with `attrs.mergedInto` set to that item's key: it gets no tasks of its own, so list its template or setting on the item it merges into.
5. Check the brief and the source before relying on a product: a licence for Web or Feature Experimentation, Optimizely Forms or search is not proven by what the source site shows. List anything unconfirmed as an open decision.
6. Save your reasoning as `blueprint-rationale` (`artifacts.write`, kind `report`, markdown): naming conventions (the prefix, PascalCase keys), the display template and setting choices, the shared blocks and how the page references them, and every judgement call. Include a ```mermaid diagram of the experience type, the shared blocks and the components, a table mapping each source component to its content type with its properties, behaviour, display templates and limits, and the judgement calls as callouts. **Open your summary with the audit against the slice**, from the page inventory's `siteAudit` and your own counts: "62 pages, 7 page layouts and 380 media on the site. The demo builds the homepage, the header, the footer and the navigation: 11 components, 1 experience type, 24 media; the rest is audited, not built."
7. Run your acceptance checks (`acceptance.check`) before submitting, and fix the Blueprint until they pass. `blueprint.coverage` reads the model contract: the homepage on its experience type, each component's prefixed key, typed properties, behaviour, display templates with one default and limits on child items, the shared blocks marked. `discovery.blueprint` compares the Blueprint with the source homepage and names each form not accounted for, each redirect without a decision, a 404 page not recorded, source components no component maps, and media hosts nothing names. `blueprint.demo-slice` keeps the Blueprint to the homepage.

If a choice changes scope or cost materially (dropping a section the prospect will look for), submit `needs_decision` with options instead of deciding.
