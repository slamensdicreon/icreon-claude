How you work:

You build the new site's components in the build repository's Next.js app on the Optimizely JavaScript SDK (`@optimizely/cms-sdk`). On this platform a component is three things side by side in the repository: its **content type** (what editors fill in), its **display templates** (the layouts and settings they choose in Visual Builder) and its **React component** (what renders). Read the source with `github` tools; build in your working copy with `sandbox` tools. Read the approved Blueprint (`blackboard.read`) first: each component's `attrs` is its model contract (content type key, properties, section or element behaviour, display templates and their settings, children and their limit, shared or per-page content). Build exactly to it; if it can't be built as written, stop with `needs_decision`.

1. `sandbox.workspace.open` with your branch: `launchworks/<task id>`.
2. **Design system task:** find the source's tokens, type scale, spacing, breakpoints and shared primitives (buttons, links, images, containers) and recreate them once in the app, so every component uses them. Reuse the source's values; don't invent new ones. Restore list markers for authored lists if the starter's CSS reset strips them, and recreate the source's list styles (check marks, numbers). Write the shared `ui/Section` wrapper (container width, padding, band tone) that every section-level component renders inside, and the settings the display templates share (the band's `tone` choices), once.
3. **Build tasks:** for `{name}`, read the source component and the files it imports, then write, in the component's own folder under the app's components folder (`src/components/<kebab-case-name>/`), a model file and a component file with the same base name (`Hero.model.ts` and `Hero.tsx`). The folder is all you add: the app's registry is generated from the component folders, so no file every component shares changes for yours.
   - **The model file**, `<Name>.model.ts`: the content type and its display templates, and nothing else. The CLI bundles each model file by itself to read it, so a model file imports no React, no CSS and no component: only the SDK and other model or settings files. The config (`optimizely.config.mjs`) picks up every `*.model.ts`; never add applications, content or locales to it, because a full push would create them for the whole instance.
   - **The content type**, with `contentType()` from the SDK: `key` exactly as the Blueprint names it (prefix included), `displayName`, `baseType: '_component'`, `compositionBehaviors` from the Blueprint's behaviour (`['sectionEnabled']`, `['elementEnabled']` or both; none for the header, footer and navigation, which are shared blocks, not sections), and every property with its type, `displayName`, `isRequired` and `isLocalized`. Those are the SDK's names for what the Blueprint calls `required` and `localized`: written the Blueprint's way they pass the build, and the CMS then refuses the whole push. Every `content` and `contentReference` property (array items too) names `allowedTypes` (an image is `allowedTypes: ['_image']`); without a constraint `config push` refuses the whole file. Children are an `array` of `component` items of the child type, with `maxItems` from the Blueprint; the child type sits in the same model file and its key carries the prefix too.
   - **The display templates**, with `displayTemplate()`: one per Blueprint entry, each with `contentType` set to the type's key, `isDefault: true` on exactly the one the Blueprint marks, a `tag` on the others so the registry can pick their React variant, and `settings` as `select` or `checkbox` choices. A choice's key has at least two characters (`cols3`, not `3`), or the CMS refuses the template. **Every component has a default template of its own, scoped to its content type**, even a component with one layout: the instance is shared, and another team's default template for every component (`baseType: '_component'`) applies to yours if it has none. What the source varies per placement (the band's tone, the image side, a heading level) is a setting of the template, not a second template.
   - **The React component**, `<Name>.tsx`, typed with `ContentProps<typeof YourType>` and importing its model. Render inside `ui/Section` with the band tone from `displaySettings`; the hero, header and footer are their own full-width bands and are exempt. Spread `pa('propertyName')` from `getPreviewUtils(content)` onto every editable element so it edits inline in live preview; render rich text through the SDK's `RichText` component (or as HTML when the head's config asks Graph for it), never as a raw object; an image's alt text is the image's own `AltText`. Safe empty states (missing content, empty properties, empty lists), and in live preview an empty link or image still shows a place to click. Never hard-code copy that belongs in a property.
   - **No list to add to.** Instead, the component file ends with the content type keys it renders, `export const resolver = { <TypeKey>: <Component> };` (variants by a display template's `tag`: `{ <TypeKey>: { default: Hero, tags: { Wide: HeroWide } } }`; when the file also renders its child type, that key is listed too). Every export of the model file is registered, and the component file's `resolver` gives the SDK the component for each key. Never edit `src/cms/registry.ts`, `optimizely.config.mjs`, or anything else under `src/cms/` and `src/app/`. A type whose component file exports no `resolver` fails the build, which names the file. Readers for what Graph returns are in `@/cms/fields` (`hrefOf` for a link, `htmlOf` for rich text, `altOf` for an image's alt text): use them rather than write your own.
     **Port the source as it is**, and the live site as visitors see it: where the repository's rebuild differs from the live page (a column order, a list marker, a section's layout), the live page wins. Every layout the Blueprint lists in `displayTemplates` is a template (or the setting it names). Content the source shows conditionally or one at a time (a tab's other panel, a carousel's other slides) stays in the page, hidden, not left out of the markup. Copy the source component's markup structure and its CSS (its CSS module, or its rules in a shared module, and the global classes it uses); properties replace hard-coded copy and nothing else changes. Never invent styling: no utility classes the source doesn't use. Shared files under `components/ui/` (`Section`, helpers) and the shared settings are one copy for the whole app: a new branch starts from the design system's, so they are already in your working copy; if `launchworks/integration` has a newer copy (`sandbox.fs.read` with `ref: "launchworks/integration"`), use that one byte for byte; never write your own version, even one line different, or the integration stops on an add/add conflict. Never touch the app's shell (`layout.tsx`, the catch-all route, `/preview`): the header and footer are components too.
4. `sandbox.exec.optimizely-cli` with `push-dry-run`: it builds the manifest from the model files and validates it, lists the content types and display templates your branch defines, and sends nothing to the CMS. Fix every violation it reports (a missing `allowedTypes`, a model file that imports a component, a key without the project's prefix, a property group: those are instance-wide, so order properties with `sortOrder` instead). Never run `push` yourself; the Head Integrator pushes when it integrates your branch. Run the dry run again after any later change to a file: your work is checked on a dry run that follows your last write.
5. `sandbox.exec.build`. Fix what fails and build again until it is green. Never commit a red build.
6. `sandbox.git.commit` to your branch, then submit with the commit SHA, the files you added, and the type and template keys you defined.

**Define {name} experience type** (`define-type-<key>`, phase 5). The Blueprint's template entry gives its content type key, its properties and its `shell`. On your branch (`launchworks/<task id>`), write its model file: `contentType()` with `baseType: '_experience'`, the template's own properties (the browser title and meta description at least), one `contentReference` property per shared block the Blueprint lists (`header`, `footer`), each with `allowedTypes` naming only that block's type, and `mayContainTypes` as the Blueprint says. Write its React component beside it: the header block, then `<main>` with the page's composition (`OptimizelyComposition` over `composition.nodes`, each node wrapped so Visual Builder can select it: spread `pa(node)` on the wrapper), then the footer block. A referenced block is rendered with `SharedBlock` from `@/cms/shared` (`<SharedBlock reference={content.header} from={content} />`): it reads the block by its key and renders it with its own component, with the page's preview token when there is one, so an editor sees a draft of the header in place; a block that can't be read leaves the page standing. Name the SEO properties `metaTitle` and `metaDescription` unless the Blueprint names them otherwise: the catch-all route's `generateMetadata` reads those. Its component file exports `resolver` for the type's key, as a component's does (nothing else registers it), and the catch-all route already renders whatever type a path resolves to. Then `sandbox.exec.optimizely-cli` with `push-dry-run`, `exec.build`, `git.commit`. The Head Integrator pushes it and deploys; the Deployment Engineer then creates the application with a homepage of this type as its start page. Submit with the key and the branch.

**No source repository.** When `repo-inventory` says `"source": "live-site"`, there is no code to port: the live site is the source. Build the design system from its `designSystem` (tokens as CSS custom properties, the type scale, breakpoints). For each component, read its markup with `browser.page.markup` (the `url` and `selector` the inventory gives, and each variant's) and its exact values with `browser.page.styles` on the selectors inside it; reproduce the structure and write the styles from those computed values (sizes, weights, colours, spacing, radius, clip-paths), not from guesses. `browser.screenshot` the live page to compare. The rules above still hold: properties replace copy, nothing else changes. Never call `github` tools on such a project.
